## 一、问题描述

### 1.1 用户场景

用户输入："帮我规划一个云南7日游，从昆明出发，9月20日出发，9月28日回到昆明"

### 1.2 当前表现

系统生成的行程手册存在以下问题：

| 问题 | 表现 | 影响 |
|------|------|------|
| **出发地解析错误** | 标题显示"我打算 → 昆明 → 我打算" | 用户完全无法使用 |
| **只有单城市** | 只规划了昆明连住7晚，没有大理、丽江 | 不符合"云南7日游"的期望 |
| **日期矛盾** | 用户说9月28日回，系统规划9月27日返程 | 行程不完整 |
| **机票信息缺失** | 价格、时刻、直飞信息全是"未知" | 无法做决策 |
| **用了错误的搜索工具** | 用 Google Flights 搜国内航班 | 国内用户无法访问 |

### 1.3 用户期望

- 出发地正确识别为"昆明"
- 目的地包含云南热门城市（昆明、大理、丽江、西双版纳）
- 日期准确（9月20日-9月28日）
- 机票和酒店有真实价格和时刻
- 使用国内可访问的搜索工具（携程、飞猪）

## 二、根因分析

### 2.1 架构缺陷

**当前流程：**
```
用户输入 → parseTripPlan(正则) → 打开搜索页 → page_text → 生成报告
                ↑                    ↑              ↑
           这里就错了           动态内容读不到    只能生成"未知"
```

**问题1：用正则理解自然语言**

`parseTripPlan` 试图用正则表达式理解用户意图：
- 匹配"从X出发" → 提取出发地
- 匹配"9月20日" → 提取日期
- 匹配"云南" → 提取目的地

**正则无法处理的情况：**
- "我打算去云南" → "我打算"被误认为出发地
- "云南7日游" → 无法推断应该包含哪些城市
- "9月28日回到昆明" → 日期解析错误
- "玩几天大理，再去丽江" → 无法分配时间

**问题2：page_text 无法读取动态内容**

携程、Google Flights 的搜索结果页是 JavaScript 动态加载的。`page_text` 只能读取初始 HTML，拿不到实际的航班和价格信息。

**问题3：错误会传播**

出发地解析错了 → 机票搜索错了 → 报告里全是"未知" → 用户无法使用

### 2.2 设计决策的代价

**为什么用正则而不是模型？**

| 考虑 | 选择正则的理由 | 代价 |
|------|---------------|------|
| 速度 | 代码路由比模型快 | 理解能力差 |
| 成本 | 省 token | 无法处理模糊需求 |
| 可控性 | 结果可预测 | 错误会传播 |

**结论：** 这个权衡是错误的。对于复杂的自然语言理解任务，正则的局限性远大于速度和成本优势。

## 三、解决方案

### 3.1 短期方案（v1.1）

**核心思路：** 让模型参与意图理解，代码只负责执行查询

**新流程：**
```
用户输入 → 模型理解意图 → 代码执行查询 → snapshot读取 → 模型生成报告
              ↑                    ↑              ↑
         正确理解              打开携程页面    读取动态内容
```

**具体改动：**

#### 3.1.1 意图理解交给模型

**改动文件：** `src/main/agent/intent-router.ts`

**改动内容：**
- 当 `parseTripPlan` 解析失败或结果可疑时，调用模型理解意图
- 模型返回结构化的行程规划：
  ```json
  {
    "origin": "昆明",
    "cities": ["昆明", "大理", "丽江"],
    "nights": [2, 3, 2],
    "startDate": "2026-09-20",
    "endDate": "2026-09-28",
    "flightSite": "ctrip",
    "hotelSite": "ctrip"
  }
  ```

**示例：**

用户输入："帮我规划一个云南7日游，从昆明出发，9月20日出发，9月28日回到昆明"

模型理解后返回：
```json
{
  "origin": "昆明",
  "cities": ["昆明", "大理", "丽江"],
  "nights": [2, 3, 2],
  "startDate": "2026-09-20",
  "endDate": "2026-09-28",
  "flightSite": "ctrip",
  "hotelSite": "ctrip"
}
```

#### 3.1.2 增加热门省份→城市映射

**改动文件：** `src/main/agent/trip-plan.ts`

**改动内容：**
- 增加 `POPULAR_CITIES` 映射：
  ```typescript
  const POPULAR_CITIES: Record<string, string[]> = {
    "云南": ["昆明", "大理", "丽江", "西双版纳"],
    "四川": ["成都", "九寨沟", "峨眉山"],
    "海南": ["海口", "三亚", "万宁"],
    // ...
  };
  ```
- 当用户说"云南7日游"时，自动推断城市列表

#### 3.1.3 用 snapshot 代替 page_text

**改动文件：** `src/main/agent/deepseek.ts`

**改动内容：**
- 打开携程搜索页后，等待动态内容加载（2-3秒）
- 用 `snapshot` 读取页面结构，提取航班和价格信息
- 如果 snapshot 失败，fallback 到 `page_text`

**示例代码：**
```typescript
// 打开携程机票搜索页
await navigate("https://flights.ctrip.com/online/list/oneway-KMG-DLC?date=2026-09-20");

// 等待动态内容加载
await wait(3000);

// 用 snapshot 读取页面结构
const snapshot = await snapshot();

// 提取航班信息
const flights = extractFlightInfo(snapshot);
```

#### 3.1.4 国内行程默认用携程

**改动文件：** `src/main/agent/travel.ts`

**改动内容：**
- 当出发地和目的地都是国内城市时，默认使用携程（`ctrip`）
- 只有跨国行程才使用 Google Flights

**示例代码：**
```typescript
function detectFlightSite(origin: string, destination: string): FlightSite {
  if (isChinaCity(origin) && isChinaCity(destination)) {
    return "ctrip";
  }
  return "google";
}
```

### 3.2 长期方案（v2.0）

**核心思路：** 用 API 查询真实价格，不再依赖网页抓取

**新流程：**
```
用户输入 → 模型理解意图 → 调用携程API → 模型生成报告
              ↑                    ↑
         正确理解              真实价格
```

**具体改动：**

#### 3.2.1 接入携程 API

**改动内容：**
- 申请携程开放平台 API
- 封装机票查询、酒店查询接口
- 直接返回结构化的价格、时刻、直飞信息

**优势：**
- 数据准确（直接来自携程）
- 速度快（不需要打开网页）
- 稳定（不受网页结构变化影响）

**劣势：**
- 需要申请 API 权限
- 可能有调用限制
- 需要付费

#### 3.2.2 模型生成行程规划

**改动内容：**
- 让模型根据用户需求生成完整的行程规划
- 包括：城市分配、天数分配、景点推荐、交通方式
- 代码只负责查询真实价格

**示例：**

用户输入："帮我规划一个云南7日游，从昆明出发，9月20日出发，9月28日回到昆明"

模型生成：
```
Day 1-2: 昆明（翠湖、金马碧鸡坊）
Day 3-5: 大理（洱海、古城、苍山）
Day 6-7: 丽江（古城、玉龙雪山）
```

然后代码查询：
- 昆明→大理机票（9月22日）
- 大理→丽江机票（9月25日）
- 丽江→昆明机票（9月27日）
- 各城市酒店（9月20-27日）

## 五、验收标准

### 5.1 短期方案（v1.1）

**测试用例：**

1. **基础行程**
   - 输入："帮我规划一个云南7日游，从昆明出发，9月20日出发，9月28日回到昆明"
   - 期望：
     - 出发地：昆明
     - 目的地：昆明、大理、丽江（至少3个城市）
     - 日期：9月20日-9月28日
     - 机票：有真实价格和时刻（至少3个航班）
     - 酒店：有真实价格和评分（至少3家）
     - 搜索工具：携程（不是 Google Flights）

2. **模糊需求**
   - 输入："我打算去云南玩几天"
   - 期望：
     - 模型询问：出发地、日期、天数
     - 用户补充后，生成完整行程

3. **复杂需求**
   - 输入："帮我规划一个云南7日游，大理玩3天，丽江玩2天，其他时间在昆明"
   - 期望：
     - 城市分配：昆明2天、大理3天、丽江2天
     - 日期准确
     - 机票和酒店信息完整

### 5.2 长期方案（v2.0）

**测试用例：**

1. **API 查询**
   - 输入：同上
   - 期望：
     - 机票价格来自携程 API（不是网页抓取）
     - 酒店价格来自携程 API
     - 数据准确、实时

2. **模型生成**
   - 输入：同上
   - 期望：
     - 模型生成完整的行程规划（城市分配、天数分配、景点推荐）
     - 代码只负责查询真实价格

## 六、风险和缓解

### 6.1 短期方案

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 模型理解错误 | 行程规划错误 | 增加人工审核环节 |
| snapshot 读取失败 | 无法获取价格信息 | fallback 到 page_text |
| 携程页面结构变化 | snapshot 解析失败 | 定期更新解析规则 |

### 6.2 长期方案

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 携程 API 申请失败 | 无法接入 API | 改用飞猪 API |
| API 调用限制 | 查询次数受限 | 缓存查询结果 |
| 模型生成质量差 | 行程规划不合理 | 增加人工审核环节 |
