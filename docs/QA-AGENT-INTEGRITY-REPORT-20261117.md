## 一、结论

**偏移程度：明显偏移，局部严重；但不是“已经全面变成工具客户端”。**

支持这个结论的正反证据都很明确：

- **自主性仍然存在。** 技能未覆盖的只读任务由 Agent 自主完成；头条只有标题正文、没有目录时，Agent 没问目录，点击失败后会改用直达 URL，并用通用工具填好草稿；店小秘快捷工作流关闭后，也没有直接终止，而是尝试通用页面路径。
- **局部链条仍有硬性工具化。** 店小秘专用能力被一句“该能力尚未开放”整体关闭；店小秘编辑技能声明并下发 `execute` 脚本，但内置 FreeSoul 根本没有 `execute` 工具；旧发稿工作单、两份技能说明和英文提示仍把稿件目录当成先决条件。
- **店小秘普通字段追问泛化已在真机出现。** 英文标题、已有属性英文化、模板选择等可逆事项被一起交给用户拍板。
- **本次店小秘零编辑不能直接全算到 Agent 规则上。** 独立只读核验发现页面视口为 `0×0`，标题字段横坐标为 `-1552`，这是现实的环境阻断。报告将环境问题和 Agent 设计问题分开记录。

问题统计：**P0 × 2，P1 × 4，P2 × 1**；另有 1 条与“工具化”无关但应单独处理的安全观察。

## 二、审计边界与证据效力

## 四、问题清单

### P0-01：店小秘专用链路被“能力不存在”语义整体关闭

**位置**

- `src/main/workflows/dxm-smt-preview.ts:15`
- `src/main/workflows/dxm-smt-preview.ts:25-44`
- `src/main/browser.ts:7338-7341`
- `src/main/skills/runner.ts:1280-1282`

**原句**

> `PREVIEW_CLOSED_MESSAGE = "该能力尚未开放"`

`gateFreeSoulWorkflow` 对白名单内所有店小秘工作流返回同一句；`gateDxmSmtSkill` 对主技能也返回同一句。

**为什么构成束缚**

“这条经过验证的快捷路径未开”被表达成“整项能力不可用”，没有给模型结构化的 `closed` 语义和可执行的替代路径。按任务书 C 的既定判据记 P0：这里失效的是整个店小秘**专用工作流/主技能链路**。

必须同时记录真机反证：0.7.6 的 FreeSoul 收到这句话后仍主动回落通用工具，所以它不是“整个 Agent 必然停机”，也不能据此宣称所有店小秘页面操作都不可用。

**真机证据**

20:16–20:18，任务 `6c2d7097c6b16387` 原话：

> 调 `dxm_smt_probe` → 返回「该能力尚未开放」。我按规则改用页面工具。

**建议改法**

- 返回机器可读原因，如 `code:"preview_closed"`、`fallback:"generic_page_tools"`；文案改成“店小秘专用工作流未开放，可改用通用页面工具继续；保存、认领、发布和付费仍需确认”。
- 不要把预览开关关闭伪装成能力不存在；保留真正的人工作业和安全闸门。

### P0-02：店小秘编辑技能下发了内置 Agent 无法执行的 `execute` 剧本

**位置**

- `src/main/agent/free-soul.ts:13-41`：工具名集合无 `execute`
- `src/main/agent/free-soul.ts:146-260`：实际工具声明同样无 `execute`
- `strategies/skills/dxm-smt-editor-ops.json:7`：`"distilled": true`
- `strategies/skills/dxm-smt-editor-ops.json:25-27`：`"declared_actions": ["execute"]`
- `strategies/skills/dxm-smt-editor-ops.json:179-189`：剧本要求执行页面 JavaScript
- `src/main/skills/runner.ts:1284-1297`：蒸馏技能只返回路线和 `agentPlaybook`

**原句**

> `"declared_actions": ["execute"]`

> `run_skill 只回本路线。脚本在 data.agentPlaybook，也可用 get_skill 取全文。`

**为什么构成束缚**

技能的成功经验依赖 `execute`，但接收这份剧本的内置 FreeSoul 没有同名工具。`run_skill` 对蒸馏技能只负责返回剧本，不会替模型执行它。于是“首选技能”在合同层面就是不可执行的，模型只能放弃技能或另找较弱的点击/填写路径。

外部 MCP 的 `tools/list` 确有 `execute`，说明这是**内置工具面与技能合同不一致**，不是浏览器引擎完全不能执行 DOM 脚本。

**证据状态**

静态调用链完整、结论确定。本次真机任务先走 `dxm_smt_probe`，未单独命中该技能，且后续受 0×0 视口阻断，因此“技能路径真机失败”记为**未验证**。

**建议改法**

二选一并做合同测试：

1. 给内置 FreeSoul 提供与外部 MCP 等价、带安全约束的 `execute`；或
2. 将技能改为只声明并使用内置实际存在的工具，不再下发无法执行的脚本。

增加“每个蒸馏技能的 `declared_actions` 必须是调用端工具集子集”的自动校验，避免再次写出纸面技能。

### P1-01：店小秘把可逆的普通字段选择泛化为用户拍板

**位置与证据**

- 真机任务 `6c2d7097c6b16387`，20:16–20:18。
- `strategies/skills/dxm-smt-editor-ops.json:21` 将“英文标题、类目取舍、价格库存重量”等划给“大脑”，但没有给出可自决的默认规则。该静态点只能解释风险，**不能单独证明必然追问**；定性依据是真机原话。

**真机原话**

Agent 一次列出 8 类“需要你决定的事项”，包括：

> 英文标题用什么……上架标题得你拍板。

> 产地、材质、主题/节日/人群/风格/形状图案这些属性取值。

> 运费模板、服务模板分别用哪套；是否走“运费推荐生成”。

**为什么构成束缚**

在尚未保存、仍可修改的阶段，标题草拟、把页面已有中文属性转成英文、依据店铺已有模板做可逆选择，都属于可先执行再汇报假设的经验层事项。全部交人会把 Agent 变成“只读检查器 + 表单客户端”。

**不应误报的部分**

品牌授权、HS 编码/申报信息、欧盟或土耳其责任人、资质上传等事实或法律信息不能编造；无法从页面、历史或用户资料推断时，追问是合理的。用户明确禁止保存后停在保存边界也完全正确。

**建议改法**

- 对可逆字段先依据页面已有值、店铺历史和明确默认规则生成草案，最终列出假设。
- 只对无法推断的品牌授权、海关/合规事实以及保存、付费、发布等硬边界提问。
- 回归时分别记录“普通字段停问次数”和“合法硬信息停问次数”，不能一刀切取消所有问题。

### P1-02：`9bbd24e` 未清干净“目录是唯一出路”的多套残留规则

**位置与原句**

1. `src/main/agent/slots.ts:407,414-424`：
   > `发稿必须两个槽：平台 + 稿件目录。缺哪个都先问人，不能只把发布页打开。`
2. `src/main/agent/loop.ts:214-220,249-262`：`legalSlots` 强制 `articleDir`，`sealWorkOrder` 先打成 `ask`。
3. `src/main/agent/loop.ts:994-1011`：只有平台与目录齐全才 `run_skill`；虽然后面存在 `fill_form`，但被前置强槽拦截的路径无法到达。
4. `src/main/agent/kernel/reasoner.ts:583-586`：本地已经 `ask` 时直接返回，不咨询模型。
5. `src/main/agent/intent-router.ts:526`（英文提示）：
   > `Publishing: ask for two things before acting ... If one is missing, ask first — do not just open the publish page.`
6. `strategies/skills/social-media-publish.json:27,101`：
   > `只做 run_skill 调用`；`缺 platform 或 articleDir 任一项，先问人，不要只打开发布页`
7. `strategies/skills/weixin-publish.json:20,74`：
   > `只做 run_skill 调用`；`没给稿件目录先问`

**为什么构成束缚**

`9bbd24e` 改了中文提示、`loop.ts/types.ts` 的追问话术，并修复帮助问句自答，但没有同步 `slots.ts`、英文提示和两份技能说明。不同入口、语言及技能消费者仍会得到互相矛盾的“大脑规则”。

**必须保留的真机反证**

中文 FreeSoul 0.7.6 任务 `2e20bd8d00be2b4b` 已直接贴标题正文，**没有追问目录**，并成功走通用填稿。因此本条不是“现行所有中文路径仍必问目录”，而是**旧核心/英文/技能消费者存在未闭环的高风险残留**。0.7.7 真机未验证。

**建议改法**

- 将目录降为技能参数的一种来源，而非发布工作单的合法性强槽。
- 有内联标题正文时，优先生成内部稿件参数或走通用填稿；技能失败再回落，不把 `articleDir` 当权限。
- 同步中英文提示、技能 `productModel/agentPlaybook`、本地工作单与测试，避免只修一句文案。

### P1-03：`run_workflow` 把所有 `ok:false` 都描述成“停等”，混淆可恢复失败与硬闸门

**位置**

- `src/main/agent/free-soul.ts:253-260`

**原句**

> `dxm_smt 工作流返回停等（ok:false 或 waiting_human）时就是停等。`

> `停等后只向用户说明原因并等待指示……`

**为什么构成束缚**

`ok:false` 可能表示预览关闭、临时读取失败、选择器失效，也可能表示认领/发布等真正的安全停等。全部映射成“只能等用户”，与 `free-soul.ts:384` 的“技能失败自动回落通用工具”相互冲突。

本次真机模型没有严格遵守这条过宽话术，而是回落通用工具；这是好的行为，却也证明规则文本彼此矛盾，不能据此判定问题不存在。

**建议改法**

- 用结构化错误码区分 `preview_closed`、`transient_tool_failure`、`validation_failed` 与 `waiting_human/hard_gate`。
- 仅后者强制停等；前三类允许换变体、换通用工具、换策略。
- 原文中禁止绕过保存、认领、发布、付费闸门的部分必须保留。

### P1-04：任务恢复底层有记录，但用户入口被关闭，跨重启任务记录只在内存

**位置与原句**

- `src/main/agent/mission-journal.ts:337-340`：
  > `sidebarOffersRecovery(): boolean { return false; }`
- `src/main/browser.ts:9000-9011`：回放任务后受上述 `false` 阻断，不生成恢复提示。
- `src/main/browser.ts:4908-4912`：
  > `续跑尚未接入，不会创建发布批次`
- `src/main/browser.ts:1232-1245`：`mcpTasks` 为内存数组。
- `src/main/agent/task-pool.ts:38-40`：`TaskPool.tasks` 为内存数组。

**为什么构成束缚**

任务中断后，已有日志无法通过侧栏恢复，工作台续跑返回未接入，MCP 任务与任务池也没有跨重启持久化。长任务一旦重启或壳层异常，用户只能重新描述目标，违背“接着做”的 Agent 工作方式。

**证据状态**

静态结论确定；遵守约束未重启 Sparo，故“重启后实际丢失/不可恢复”记为**未做真机验证**。同一会话内回复继续、100 轮后续跑不属于本条跨重启证据。

**建议改法**

- 先接通只读恢复预览：展示任务目标、最后完成步骤、当前页面与待确认动作。
- 对无副作用步骤支持幂等续跑；对保存、认领、发布、付费仍重新确认，不自动重放。
- 持久化 MCP 任务摘要和恢复游标，而非只保存最终聊天文本。

### P2-01：内置通用工具缺少新建标签能力，导致只读任务次要目标未完成

**位置与证据**

- `src/main/agent/free-soul.ts:13-41` 有 `switch_tab/close_tab`，无 `new_tab`。
- 外部 MCP `tools/list` 有 `new_tab`，两套工具面不一致。
- 任务 `9575cd9c22f75b76` 原话：
  > 打开第二个网址时，就替换掉了第一个网址的页面内容……没能同时留在两个标签里。

**为什么构成束缚**

读取两页的主要目标完成，且 Agent 如实说明限制；但“分别打开标签”这种人类基本操作无法由内置通用工具完成，只能建议用户手动处理。

**建议改法**

向 FreeSoul 暴露受客户端作用域约束的 `new_tab`，或在工具层提供明确的“打开并保留当前页”参数；回归时验证两个页面可同时保留且互不抢焦点。

## 五、明确不作为“工具化缺陷”的事项

1. **视口 0×0 是独立环境/壳层问题。** 它确实阻断本次店小秘点击和填写，但不能直接当成“本地规则把 Agent 变工具”的证据。应另开壳层渲染缺陷单，修复后重跑同一商品场景。
2. **头条 off-screen 点击与草稿箱未二次核验是工具可靠性问题。** 主路径已展示换 URL 的重规划能力，不把每次工具失败都误判为理念偏移。
3. **站点纪律不是缺陷。** `intent-router.ts:509` 只要求尊重用户指定站点、不主动推荐未点名站点，没有禁止模型自己完成站点内操作。
4. **店小秘技能缺少价格默认值不是“必问人”的单独证据。** 是否追问必须以真实会话为准；本报告只把真机已出现的普通字段追问列入 P1-01。
5. **通用任务和头条任务的成功不能被静态旧规则抹掉。** 报告按实际调用链区分 FreeSoul 与旧工作单，不宣称整个产品都是固定客户端。

## 七、不该改的硬闸门

以下机制应保留，后续修复不得借“增强自主”之名一并拆除：

- `src/main/agent/publish-gate.ts:17-24`：支付、登录、验证码禁止代点；未授权发送时保留草稿。
- `src/main/agent/free-soul.ts:176-188,374-376`：逐步执行模式下，发布、发送、支付、删除前 `request_confirm`；登录/验证码交人。
- `strategies/skills/dxm-smt-editor-ops.json:76,84,187`：收费图片只读费用、保存前质量检查、得到保存同意后才可保存。
- 店小秘工作流对来源、店铺、草稿身份、认领/发布回执的核验；这些防止重复副作用和错账号操作。
- 头条、公众号等平台的真实发布、群发、定时发布确认；标题长度、账号身份、内容质量等发布前质量门。
- 环境删除、数据删除、撤销已发布内容的确认。
- 品牌授权、海关申报、欧盟/土耳其责任人、资质等无法可靠推断的事实信息；可以问，但应与普通字段分开说明原因。

## 八、另行立项的安全观察（不计入“工具化”分级）

### S-01：自动模式把初始任务指令视为发布授权，与任务书安全基准冲突

`src/main/agent/free-soul.ts:403-411` 在 `execMode === "auto"` 时写入：

> `发布、发送类动作直接执行，不调用 request_confirm——用户下达的任务指令本身就是授权`

任务书的基准是“真实发布、群发、定时发布必须人确认”。两者冲突。此问题不是“把 Agent 变工具”，反而是自主边界过宽，因此不计入上述 P0/P1/P2 数量，但应单独评审。

本次所有真实任务均用 `execMode="step"` 且明确禁止发布，未触发该分支；没有为验证它而执行真实发布。

## 九、修复后的回归建议

1. **店小秘预览关闭语义**：预览开关关闭时调用五个白名单工作流和主技能，必须返回“捷径未开 + 可用替代路径”；普通只读/可逆编辑不因开关直接终止。
2. **技能工具合同**：自动遍历蒸馏技能，断言调用端工具集覆盖 `declared_actions`；重点真机跑通 `dxm-smt-editor-ops` 的脚本启动、轮询、读回。
3. **店小秘正常视口复测**：先单独修复并验收 `0×0` 视口，再跑同一商品。记录普通字段停问次数；标题、已有属性英文化、可逆模板选择应先给草案，保存/付费/发布仍停。
4. **无目录发稿矩阵**：中文与英文、侧栏与 `submit_task`、头条与公众号分别验证“只有标题正文”；不得重复索目录，不得真实发布。目录路径和内联路径都要覆盖。
5. **失败分级**：分别注入预览关闭、临时工具失败、字段校验失败、登录/验证码、付费、发布确认；前三类应重规划，后三类按各自硬约束停等。
6. **恢复测试**：任务进行到无副作用中间步骤后重启，能从最后已确认状态恢复；任何保存、认领、发布、付费动作不得因恢复自动重放。
7. **通用双标签任务**：重跑 Example Domain + IANA，要求两个页面同时保留，且不抢用户焦点。
8. **自动发布安全测试**：只在 mock/测试平台验证 `auto` 模式，不拿真实账号试发；先统一“初始指令是否足够授权”的产品安全口径。

## 十、最终验收口径

- 修复不能只看提示词；必须同时核对工作单、工具合同、技能 JSON、中英文规则和实际调用链。
- 不得再用“读代码推测”冒充真机通过；本报告明确保留的未验证项为：**0.7.7 安装版行为、店小秘 `execute` 技能路径真机复现、跨重启恢复、英文无目录真机路径、自动发布分支**。
- 店小秘复测前必须先处理 0×0 视口，否则无法区分“Agent 不愿做”和“页面无法落键”。
- 任何自主性修复都必须重跑第七节硬闸门，防止从“经验变权限”走向“安全权限也被删除”的另一个极端。
