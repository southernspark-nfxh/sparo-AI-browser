## 一、为什么要做这次 QA

Sparo 的设计初衷不是"一个能点网页的客户端"，而是一个**智能 Agent**：用户给目标，它自己判断怎么做、遇到阻碍自己换办法、只在真正不可逆的地方停下来找人。

最近几次修改（Trae 与 Cursor 都有）出现了同一种偏差：**把"已验证的成功路径"写成了"唯一合法路径"**，把"经验"编码成了"权限"。表现出来就是：

- 技能没覆盖到，就停下问人，而不是用通用工具自己想办法；
- 能力开关没打开，就宣告"这件事不能做"，而不是"换一条路做"；
- 普通字段选择（品牌、价格、模板）被当成"必须用户拍板"；
- 一失败就终止任务，没有重试、降级、换策略。

`9bbd24e` 的提交说明已经承认过一次：

> **0.7.4 把稿件目录写成唯一出路**，侧栏听到平台就复读索要目录，堵掉了「直接贴标题正文」这条路

那次只修了发稿一处。**同样的病很可能还在店小秘、发布、采集等链路上。** 本次 QA 要把这个病整体扫一遍。

## 二、审计的判定基准（必须先统一）

### 2.1 Agent 应有的四层结构

| 层 | 内容 | 是否允许本地硬编码 |
|---|---|---|
| 目标 | 用户要完成什么 | 否，由模型理解 |
| 硬约束 | 不可逆、花钱、对外发布、登录/验证码 | 是，必须拦 |
| 经验 | skill = 已验证的首选路径 + 已知坑 | 是，但只能是**建议** |
| 失败处理 | 换变体 → 换通用工具 → 换策略 → 最后才问人 | 否，由模型重规划 |

**唯一合格的标准**：技能是地图，不是围栏。

### 2.2 明确不算缺陷的东西（防止矫枉过正）

以下拦截是**正确设计**，审计时不得判为"束缚"：

- 付费翻译、保存商品、认领、提交平台必须人确认；
- 真实发布、群发、定时发布必须人确认；
- 删除环境、删除数据、撤销已发布内容必须人确认；
- 登录、验证码、支付密码不代填；
- 发布前的质量门（标题长度、话题数量、账号身份核对）。

**只有**当这些闸门被泛化到"普通字段选择"或"非不可逆动作"时，才算缺陷。

## 三、审计维度与检查项

每个维度都要给出：文件 + 行号 + 原句 + 判定 + 证据。

### A. 技能是否被写成唯一路径

- 检索所有 `strategies/skills/*.json` 与 `src/main/agent/*.ts` 中的措辞：
  `必须`、`只能`、`不得`、`唯一`、`不要用`、`禁止`、`否则失败`。
- **不合格样例**：`"发稿前必须问齐两样……缺一样就先问"`（0.7.4 已修，需确认无残留）。
- **合格形态**：`"首选 run_skill；命中失败或未命中时回落通用工具，不因技能问题中断任务"`。
- 重点核对：`dxm-smt-editor-ops`、`dxm-crawl-prep`、`social-media-publish`、`weixin-publish`。

### B. 失败是否中断任务

- 查技能执行失败的分支：`src/main/skills/runner.ts`、`src/main/agent/runtime.ts`、`src/main/agent/loop.ts`。
- 判定问题：失败后是①重试变体 ②回落通用工具 ③换策略，还是直接 `return` 错误并停。
- 需确认 `free-soul.ts` 第 383 行的回落原则是否真的在任何失败分支都生效，还是只在提示词里写着。

### C. 门禁语义是否把"捷径未开"说成"能力不可用"

- 核对 `src/main/workflows/dxm-smt-preview.ts` 的 `PREVIEW_CLOSED_MESSAGE` 原文。
- 判定标准：返回文案必须让模型理解为"这条快捷路径关闭，可改用通用工具完成"；若只说"该能力尚未开放"，视为 P0 缺陷。
- 同时检查 `publish-gate.ts` 的拒绝文案是否同样问题。

### D. 追问边界是否被泛化

- 检索所有 `ask` / `slotAsk` / `needsConfirm` 的产生条件。
- 逐项分类：该问题属于"硬约束"还是"字段级选择"。
- **不合格样例**：品牌、类目属性、零售价、运费模板、服务模板、关税选项被当成必问项。
- 合格做法：按店铺历史/页面已有值/技能默认规则自决，并在最终汇报注明假设。

### E. 本地规则是否强行覆盖模型判断

- 查 `src/main/agent/kernel/reasoner.ts` 是否存在本地启发式改判模型 `ask` 决策的逻辑。
- 查 `intent-router.ts` 是否有"没命中就固定话术"的分支。
- 判定：模型是大脑，本地只做合法性校验和安全拦截，不做业务决策。

### F. 工具面是否与人类操作等价

- 对照 `tools/list`：`click`、`fill`、`click_text`、`menu_click`、`execute`、`navigate`、`upload`、`select`、`snapshot` 是否对技能场景全部可用。
- 检查是否存在"某站点禁止使用通用工具"的硬编码。
- 判定：只要不越过硬约束，任何人类能做的页面操作，Agent 都应该能做。

### G. 任务可恢复性

- 任务中断、页面刷新、技能半途失败后，是否有续跑入口（`--from`、mission 状态、草稿接管）。
- 判定：不能要求用户从头再来，也不能因为一次失败就整单作废。

### H. 增量提交逐条定性

对下列 commit 逐条判断"增强自主 / 收紧为工具 / 中性"，并给出理由：

## 五、取证方法

- 代码：`git show <commit>`、`Grep` 关键词、逐函数阅读调用链。
- 行为：**必须真机复现**，不要只读代码下结论。至少做这三次真实会话：
  1. 打开店小秘编辑页，让它"把当前商品编辑到可以发布"——记录它停了几次、每次问什么。
  2. 给一个只有标题正文、没有目录的发稿任务——记录它是否只问一次并给出多条走法。
  3. 让它执行一个技能未覆盖的浏览器任务——记录它是自己想办法还是直接说不会。
- 证据格式：`文件:行号` 原句 + 会话时间 + 侧栏原话引用。**不得编造真机结果。**
