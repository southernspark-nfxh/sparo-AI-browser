# Sparo 电商自动化三阶段开发路线

> 版本：v1.0  
> 日期：2026-11-07  
> 性质：开发路线与验收标准，不代表现行功能已经具备  
> 上位方案：[Sparo 电商与多平台运营产品战略方案](./ECOMMERCE-PRODUCT-STRATEGY.md)  
> 证据边界：已核对现行代码、技能记录和平台官方文档；本轮尚未重新登录真实后台，也未执行真实商品发布

## 1. 路线结论

三个阶段依次完成三次能力跃迁：

| 阶段 | 最终目标 | 用户得到的结果 | 进入下一阶段的必要条件 |
|---|---|---|---|
| **第一阶段：单平台闭环** | 在店小秘把已合法采集的商品整理、翻译并发布到指定速卖通店铺 | 一个可核验的在线商品链接；失败时有明确原因和接管入口 | 真实黄金场景通过，假完成和重复发布均为 0 |
| **第二阶段：一份素材，多平台复用** | 同一商品素材生成速卖通与第二个平台的独立版本并分别发布 | 公共素材只录入一次，各平台结果独立可验收 | 跨平台不串字段、不串店铺，单平台失败不误报整单成功 |
| **第三阶段：多平台执行中控台** | 多商品、多平台、多窗口统一执行，并接入选品证据和自媒体复用 | 一个聊天框管理一批任务，用户主要处理确认与异常 | 批量任务仍可逐项验收，页面变化能安全降级，持续交活得到验证 |

第一阶段不追求“全自动无人值守”，而追求：

> **Sparo 做完能安全自动化的步骤，把必须由人决定的事项集中交给用户，最后拿到真实商品回执。**

## 2. 第一阶段的真实业务链路

### 2.1 工作范围

当前链路定义为：

**1688 合法授权货源 → 店小秘数据采集 → 通用采集箱 → 认领到指定速卖通店铺采集箱 → 速卖通商品编辑与翻译 → 发布前检查 → 用户确认 → 提交发布 → 平台审核/在线商品回执。**

店小秘官方文档支持这条主流程：1688 跨境铺货或链接采集后，商品先进入数据采集的未认领列表，再认领到平台店铺采集箱，随后编辑发布；采集 1688 需要授权。[cite:1][cite:2][cite:3]

第一阶段默认从“用户已经授权、商品已经进入店小秘”开始。1688 法律声明对第三方智能体或自动化程序的访问、调用和操作设有明确许可要求，因此不把 Sparo 直接自动操作 1688 网页作为默认第一步，也不绕过验证码或人机识别。[cite:5]

### 2.2 不是同一件事的五个状态

| 状态 | 含义 | 能否算第一阶段最终完成 |
|---|---|---|
| `draft_ready` | 编辑页字段已齐，尚未保存或提交 | 否 |
| `saved_draft` | 已保存到店小秘草稿或待发布区 | 否 |
| `submitted_pending_review` | 已提交平台，有提交回执，仍在审核或处理中 | 否，只能算已提交 |
| `published_online` | 已获得在线商品链接，或在平台在线商品中读回到同一商品 | **是** |
| `failed_or_waiting_human` | 缺资料、无权限、页面异常、发布失败或等待人处理 | 否 |

“点过发布按钮”不是结果。若平台异步审核尚未结束，任务必须保持待审状态，不能提前关单。

### 2.3 用户看到的最简交互

1. 用户说：“把采集箱里的这个商品上到我的速卖通店铺。”
2. Sparo 返回一张计划卡：来源商品、目标店铺、执行步骤、需要用户决定的价格/资质/发布事项。
3. Sparo 后台执行，不抢占用户正在使用的页面。
4. 缺少合法必填信息时，集中显示“待我处理”，而不是反复试错。
5. 发布前展示摘要，用户明确确认后才提交。
6. 最终只显示三类结果：**在线商品链接、平台处理中、需要我处理**。详细日志可展开，但不占主界面。

## 3. 现有基础与缺口

### 3.1 可以复用的基础

| 现有资产 | 已覆盖 | 不能误判为已覆盖 |
|---|---|---|
| [dxm-crawl-prep.json](../strategies/skills/dxm-crawl-prep.json) | 通用采集箱入口、编辑页保护、图片改尺寸、文字翻译、收费功能确认 | 不认领、不自动保存、不覆盖速卖通发布回执 |
| [dianxiaomi.ts](../src/main/workflows/dianxiaomi.ts) | 弹窗处理、图片菜单、图片/文字翻译、部分页面操作经验 | 分类、属性、SKU、模板仍是缺口；结尾要求用户手动保存 |
| [listing-playbook.ts](../src/main/workflows/listing-playbook.ts) | 草稿保护、翻译区分、星号必填和人工审核等经验 | 固定主图数量、固定 SKU 公式不能作为所有商品的默认规则 |
| [dianxiaomi-smt.ts](../src/main/qa/dianxiaomi-smt.ts) | 标题、部分价格库存、图片和提交按钮的基础检查 | 不能证明动态必填项齐全、翻译正确、业务值合理或发布成功 |
| 新核心 `request_confirm` | 发布前可形成明确确认往返 | 不能替代商品字段 QA 和发布后回执 |

### 3.2 必须先纠正的旧假设

- 当前 [features.ts](../src/main/features.ts) 将旧店小秘垂直工作流固定禁用。**不能只打开开关就宣称第一阶段完成。**
- “主图必须恰好 6 张”不是所有商品都应机械执行的业务决策。官方刊登说明给出的是主图上限和格式等规则，实际处理应服从当前类目、素材质量和用户策略。[cite:4]
- 旧 SKU 定价公式包含固定加价和汇率/费用假设，不能直接复用为默认价格。
- “文字偏英文”不等于标题、属性、SKU 和描述翻译正确。
- “保存成功提示”不等于平台已接受商品，“平台已接受”也不等于商品已上线。
- 旧流程的 `best_effort` 可以继续作为异常分类经验，但不能作为关单依据。

## 4. 第一阶段的小目标与开发任务

第一阶段采用四个可交付版本，每个版本都能独立验收，避免最后才发现整条链路不通。

### 4.1 P1-A：人工基线与只读识别

**小目标：Sparo 能看懂当前商品、所在页面和下一步，不修改真实草稿。**

任务包：

1. 在获得用户授权的测试店铺中，由人工完整走完一次“采集箱 → 认领 → 编辑 → 发布 → 在线商品”。
2. 记录每一步 URL、页面用途、商品标识、字段变化、按钮文案、回执和最终链接，形成脱敏基线。
3. 建立四类页面识别：通用采集列表、通用采集编辑、速卖通平台采集箱、速卖通商品编辑/结果页。
4. 只读提取来源商品 ID、店铺、标题、当前草稿状态和页面必填项。
5. 识别登录失效、无权限、验证码、页面未加载完成和入口变化，并安全停等。

完成标准：

- 同一商品多次识别结果一致，不把列表行、编辑页和结果页混为一谈。
- 页面上看不出目标店铺或商品身份时不执行动作。
- 全程只读，不产生认领、保存或发布副作用。

### 4.2 P1-B：可恢复的单商品工作单

**小目标：用户不再需要告诉 Sparo “现在做到哪一步”，系统能保存现场并续跑。**

任务包：

1. 建立单商品工作单，至少保存：
   - 来源商品与来源链接；
   - 目标平台、目标店铺；
   - 通用箱记录 ID、认领后草稿 ID、平台商品 ID；
   - 当前页面类型和当前状态；
   - 字段快照、用户确认记录、平台回执和最终链接。
2. 每一步采用“观察 → 执行 → 读回”的三段式结果，禁止只记录工具调用成功。
3. 为认领、保存、发布建立幂等检查：重试前先查目标位置是否已有同一商品。
4. 支持暂停、继续、人工接管和从最近可靠状态恢复。
5. 新增会改变任务走向或提前关单的本地判断前，先登记到 [DECISION-POINTS.md](./DECISION-POINTS.md)。

完成标准：

- 中途关闭任务后，能恢复原工作单而不是重新认领。
- 任一步失败都保留已完成的编辑内容和人话原因。
- 不出现“一个按钮点击成功，所以整单完成”的状态跳转。

### 4.3 P1-C：定位与认领到指定速卖通店铺

**小目标：从通用采集箱把正确商品认领到正确店铺，并进入正确的平台编辑页。**

任务包：

1. 按用户指定商品、来源 ID 或当前行定位唯一样本；多结果时让用户选择。
2. 读取目标店铺，不允许默认选择列表第一家店。
3. 执行认领前检查是否已存在于目标速卖通采集箱。
4. 认领后读回平台采集箱记录，保存新草稿 ID 与店铺绑定。
5. 打开编辑页时保留原列表标签，禁止刷新或替换正在编辑的草稿。
6. 对批量认领保持禁用；第一阶段只做单商品，避免误操作整页。

完成标准：

- 认领后能够通过草稿 ID、来源信息或读回内容证明是同一商品。
- 重复执行不会生成第二份相同草稿。
- 无目标店铺、店铺授权失效或认领入口变化时暂停，不乱点其他入口。

### 4.4 P1-D：动态字段编辑与安全翻译

**小目标：形成一份可提交前审核的速卖通商品草稿。**

店小秘官方刊登文档表明，分类、品牌、星号属性、变种、价格、库存、包装、模板和合规信息会受类目与页面条件影响；运费模板还需要先在速卖通后台创建并同步到店小秘。[cite:4] 因此编辑器必须按当前页面动态检查，不能写死一张固定字段表。

任务包一：页面模型与字段读写

1. 按“基本信息、分类、属性、图片、SKU/变种、价格库存、包装、物流模板、描述、合规信息”分组读取。
2. 使用字段标签、控件关系和当前值定位，不只依赖固定坐标或 DOM 序号。
3. 原生设置 input/textarea 值并派发必要事件；禁止逐字循环填表。
4. 对 Ant Design 下拉、共享弹层和屏幕外菜单建立统一打开、选择、读回、关闭流程。
5. 分类树选择叶子节点后，重新读取该类目动态出现的必填属性和资质要求。

任务包二：图片与翻译

1. 分别记录主图、变种图、描述图的处理状态，不能以主图完成代表全部图片完成。
2. 图片改尺寸后抽样读回尺寸；图片翻译后检查处理结果和失败张数。
3. 文字一键翻译与图片翻译分开执行、分开验收。
4. 图片翻译、图片白底等可能消耗秘豆或付费的功能，执行前单独确认；拒绝后走人工处理，不反复弹出。
5. 翻译后读回标题、关键属性、SKU 和描述，标记空译文、残留中文、长度超限和变量丢失；语言检测只用于提示，不冒充语义质量审核。

任务包三：业务字段与人工闸门

1. 价格、币种、货值、库存、重量、包装尺寸、运费模板和资质不由模型臆造。
2. 能从授权来源可靠读取的值保留来源；需要经营决策的值进入“待我处理”。
3. 无运费模板、无类目权限、无品牌资质时，明确指出需要用户在哪个后台处理。
4. 第一版允许多个SKU，但不要求自动推导定价；先支持用户确认的统一规则或逐SKU值。

完成标准：

- 所有当前页面星号项都有值或有明确人工缺项。
- 修改后的标题、分类、属性、SKU、价格库存和模板均可读回。
- 图片和文字翻译状态分别可查，不把付费功能未执行写成已完成。
- 无法安全决定的业务值会停问，不会用固定公式补齐。

### 4.5 P1-E：发布前 QA、确认、发布与回执

**小目标：用户只确认一次，Sparo 能区分保存、提交、待审和上线。**

任务包：

1. 发布前 QA 至少覆盖：
   - 商品、店铺和页面身份；
   - 当前类目及全部动态必填项；
   - 标题长度和翻译异常；
   - 图片数量、格式、尺寸样本及失败项；
   - SKU、价格、库存、包装和模板；
   - 品牌、类目权限及页面展示的合规要求；
   - 未保存修改和未读回字段。
2. QA 结果只有 `pass`、`waiting_human`、`fail`，不使用“尽力完成”冒充通过。
3. 发布确认卡展示店铺、标题、类目、价格区间、库存合计和关键风险；用户明确确认后才点击发布。
4. 点击后先查重复提交，再读取平台回执；超时不能立即判失败并重发。
5. 按顺序核查：店小秘待发布/失败列表、平台提交记录、在线商品列表或商品链接。
6. 获得商品 ID、平台回执或在线商品读回后，才进入对应终态。
7. 发布失败保留失败原文、字段定位和续跑入口，不自动换店、不自动再次发布。

完成标准：

- QA 缺项时发布按钮不会被自动点击。
- 用户未确认时无发布副作用。
- `published_online` 必须有商品链接或在线商品读回证据。
- 提交后超时经过查重和结果查询，不产生重复商品。

### 4.6 P1-F：真机加固与安装包验收

**小目标：从开发环境演示变成用户可持续使用的单平台工作单。**

任务包：

1. 将速卖通链路黄金场景加入 [QA-GOLDEN-SCENARIOS.md](./QA-GOLDEN-SCENARIOS.md)，底账记录工作单状态、回执和商品链接。
2. 单测覆盖状态机、动态必填项、确认门、幂等和页面识别；单测不能代替真机场景。
3. 调试版完成全部受影响场景后再打包；安装包除复测电商场景外，至少回归现行 G1、G2、G3。
4. 侧栏按钮逐项自点：点得到、下一步原地出现、暂停可续跑、控制台无报错。
5. 确认后台执行不抢焦，完成只提醒；异常不会把用户当前网页替换掉。

阶段退出口径：

- 在授权测试店铺完成连续 10 次真实黄金执行，完整成功率目标不低于 90%；这是验收目标，不是当前能力声明。
- 假完成率、重复发布事故均为 0。
- 每次“上线成功”均有可独立打开或读回的商品证据。
- 登录、验证码、付费、缺资质、发布失败和页面变化均能正确停等或接管。
- 用户不看网页过程，仅凭任务卡也能知道结果和下一步。

若平台没有可用测试环境，真实发布会留下真实商品。验收样本、发布数量和后续下架/删除均需用户安排与确认，不能为了凑次数自动创建或删除商品。

## 5. 第一阶段技术难点与对应解法

| 技术难点 | 错误做法 | 第一阶段的解法 |
|---|---|---|
| 通用箱与平台箱身份衔接 | 仅凭标题认为认领成功 | 保存来源 ID、认领后草稿 ID，并读回店铺与商品关系 |
| 编辑页草稿易丢 | 刷新、离开、替换当前标签后重进 | 页面锁与标签绑定；来源页另开标签；动作后原地读回 |
| 分类决定动态字段 | 用固定字段清单检查所有商品 | 选叶子分类后重新读取必填项和资质要求 |
| 共享下拉与屏幕外菜单 | 连点坐标、强制改样式后直接提交 | 定位当前控件与弹层，选择后读回，失败关闭旧弹层再重试 |
| 图片范围不一致 | 主图处理完就标记全部图片完成 | 主图、变种图、描述图分别记录处理与失败状态 |
| 翻译不等于可发布 | 只检测是否出现英文 | 文字/图片分开验收，检查空译文、残留、长度和SKU变量 |
| 经营字段不能猜 | 固定公式自动定价、随便选模板 | 来源值可追溯；经营决策进入人工待办 |
| 保存与发布是不同系统状态 | 点击发布就关单 | 草稿、已提交、待审、上线、失败分别建模 |
| 超时重试可能重复发布 | 立即再次点击发布 | 先查平台记录和已有商品，再决定是否续跑 |
| 页面升级 | 继续死点旧按钮或随意尝试相似按钮 | 语义重定位；无法确认时保留现场并交人判断 |

建议内部把每个动作的结果拆成三层：

- **observed**：看到了什么；
- **changed**：实际改变了什么；
- **verified**：通过什么读回或回执证明改变生效。

这三层也是后续页面变化适应、审计和跨平台复用的共同底座。

## 6. 第一阶段真机黄金场景

| 编号 | 场景 | 必须验收的结果 |
|---|---|---|
| E1 | 无变种、资料齐全的普通商品 | 正确店铺、草稿读回、确认后发布、在线链接 |
| E2 | 多变种商品 | SKU 不串行，价格库存逐一读回，规格变量翻译未丢失 |
| E3 | 分类后出现新的星号属性 | 能发现新增必填项；缺资料时停在人工待办 |
| E4 | 无品牌/类目资质 | 不虚构资质，不点发布，给出明确处理入口 |
| E5 | 无可用运费模板 | 不随机选模板，说明需先在速卖通创建并同步 |
| E6 | 用户拒绝付费图片翻译 | 不扣费、不重复请求，图片项保持未完成并说明影响 |
| E7 | 登录失效或验证码 | 安全停等，用户处理后从原工作单续跑 |
| E8 | 保存成功但发布被平台拒绝 | 保存草稿与发布失败分开显示，保留平台错误原文 |
| E9 | 发布点击后超时 | 先查重和查回执，不重复发布，最终状态可核验 |
| E10 | 入口改名或动态弹层变化 | 能安全重定位则继续；不能则暂停，不死点、不误提交 |
| E11 | 任务中断后说“继续” | 回到同一商品同一店铺，从断点继续，不重新认领 |
| E12 | 安装包完整链路 | 与调试版同样获得真实回执，并完成 G1–G3 回归 |

## 7. 第二阶段：一份素材，多平台复用

### 7.1 阶段目标

以第一阶段验证过的商品素材和工作单为底座，新增第二个电商平台。优先候选为 Ozon，但最终选择取决于真实用户店铺、授权条件、类目样本和第一阶段用户反馈，不预先为了平台数量而铺开。

用户目标：

> “这个商品已经整理好了，再给我上到另一个平台；公共素材不要让我重新填。”

### 7.2 核心开发任务

1. **商品主素材包**：把来源图片、原始标题、属性、SKU、成本和来源信息与平台字段分离。
2. **平台变体**：速卖通和第二平台分别保存分类、属性映射、译文、图片、价格库存和模板，不互相覆盖。
3. **规则映射**：公共字段尽量复用，平台专有字段单独列入待办；映射依据和人工修改可追溯。
4. **集中差异预览**：用户只看两个平台的不同项、缺项和风险，不重读整份商品。
5. **串行多平台执行**：第二版先串行，逐平台确认、逐平台回执；一个平台失败不阻断另一个已完成结果。
6. **跨平台幂等**：以“素材 × 平台 × 店铺”为最小身份，防止在错误店铺重发。
7. **素材版本**：源素材修改后生成新版本，不静默改动已发布商品。

### 7.3 第二阶段验收

- 同一商品只输入一次公共素材，两个平台各自得到独立结果。
- 两个平台的分类、价格、语言和模板不会串字段。
- 一个平台待审、另一个平台失败时，任务卡不会显示整单成功。
- 重试任一平台不会重复创建商品，也不会重复执行另一平台。
- 用户能查看“哪些内容复用了、哪些内容因平台规则而改变”。

## 8. 第三阶段：多平台执行中控台与业务闭环

第三阶段分三步扩张，避免批量、多窗口和选品同时失控。

### 8.1 P3-A：批量与多窗口

- 多商品、多平台任务矩阵；
- 后台队列、限流、标签隔离和单任务取消；
- 一个聊天框查看全部任务；
- 集中异常收件箱：登录、验证码、缺资料、确认、页面变化；
- 跨任务素材、账号、店铺和结果隔离；
- 批量场景仍逐项保存回执，不以队列结束代替完成。

### 8.2 P3-B：页面变化适应与技能健康度

- 用语义用途识别入口、字段和提交动作；
- 区分未加载、无权限、入口改名、流程升级和风控拦截；
- 技能版本、最后验证时间、已知缺口、失败样本和回退率可追踪；
- 能安全找到等价路径才继续，否则保留现场等待人工；
- 本机经验只留本机，不用个别成功样本宣称普遍适配。

### 8.3 P3-C：选品证据与自媒体复用

电商侧补齐：

- Google Trends、行业信息、合法货源和竞争信息的证据卡；
- 成本、运费、税费和合规资料的人工确认；
- 从证据卡一键生成商品工作单；
- 发布后状态与经营结果回收，为下一轮人工决策提供依据。

自媒体侧复用：

- 把“商品主素材”抽象为通用素材包；
- 把“商品平台变体”复用为标题、正文、封面、话题和声明的平台变体；
- 复用登录态、任务编排、发布确认、异常接管和逐平台回执；
- 先做一份主稿到两个平台的串行闭环，不做批量同质群发、刷量或无人值守账号矩阵。

### 8.4 最终产品形态

最终仍只让用户理解四个对象：

| 对象 | 用户看到的内容 |
|---|---|
| 素材 | 商品、稿件、图片、视频、来源和版本 |
| 任务 | 要发布到哪些平台、当前进行到哪里 |
| 待我处理 | 登录、确认、缺资料、价格和异常 |
| 结果 | 在线链接、待审状态、失败原因和续跑入口 |

底层可以增加平台、队列、技能和规则，但主界面不演变成复杂 ERP 或流程设计器。

## 9. 统一验收指标与开发纪律

### 9.1 指标

- 北极星：**每周被用户验收的有效工作单数**。
- 完整工作单成功率：所有要求平台都取得相应真实结果。
- 假完成率：缺回执、缺链接或缺计划步骤却声称完成，目标始终为 0。
- 重复发布事故：目标始终为 0。
- 人工接管次数：按登录、验证码、缺资料、经营确认和页面异常分类。
- 技能回退率：技能失效后转为临场操作或人工处理的比例。
- 持续交活与付费：用户是否继续提交真实任务，而不只看首次演示。

### 9.2 开发纪律

1. 每阶段先完成真实工作单，再增加平台数量和界面功能。
2. 不用单测绿代替真机黄金场景，不用侧栏文案代替底账和平台回执。
3. 不把旧工作流的 `best_effort` 当作成功，不为提高自动化率而取消必要确认。
4. 不重做店小秘已有的 ERP、通用采集、图片和翻译能力；Sparo 负责把流程、异常和结果连起来。
5. 不直接自动操作未获许可的货源平台，不绕过验证码、访问限制或平台风控。
6. 不在第一阶段同时开发多平台并行、选品大盘和自媒体矩阵。
7. 页面无法安全理解时，暂停比盲目执行更合格。

## 10. 当前下一步

开发从 **P1-A 人工基线与只读识别** 开始，第一项真机任务是：

> 在用户授权的测试店铺中，选定一个资料齐全、无复杂变种的真实商品，人工走通并记录从通用采集箱到速卖通在线商品的完整过程；随后让 Sparo 只读复现页面识别，不修改、不认领、不发布。

该基线一旦完成，后续每个开发任务都能与真实页面和真实回执对照，避免继续围绕旧按钮脚本局部补丁式开发。
