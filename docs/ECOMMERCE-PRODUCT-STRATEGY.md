# Sparo 电商与多平台运营产品战略方案

> 版本：v1.0  
> 日期：2026-11-06  
> 性质：产品战略与阶段规划，不代表现行功能已经全部具备  
> 研究方式：公开资料案头调研 + Sparo 现行产品能力分析；尚未开展目标用户一手访谈

## 1. 战略结论

### 1.1 产品定位

**Sparo 是面向电商与多平台内容运营者的自动化执行中控台：用一个聊天框管理多个平台后台，把素材采集、加工、翻译、编辑、上品和发布串成可验收的工作流。**

面向用户的简短表达：

> **一个聊天框，管好所有平台的上品与发布。**

Sparo 不是通用 AI 浏览器，不是新的 ERP，也不是单纯的一键群发工具。浏览器是执行环境，真正交付的是：

**素材包 + 工作单 + 平台技能 + 人工确认 + 执行回执。**

### 1.2 人群顺序

1. **主人群：中小电商、跨境电商运营者和店长。** 一人或一个小团队需要重复处理商品、素材和多个平台后台。
2. **副人群：多平台自媒体创作者和小型内容团队。** 需要把一份内容安全、合规地适配到多个平台，并处理每个平台的结果。
3. **生态人群：外部 Agent 和技能开发者。** 通过 MCP 和平台技能放大执行能力，但不是首要付费定位。

### 1.3 共同本质

电商与自媒体不是两套产品。两者都可以抽象为：

> **一份素材 × 多个平台 × 不同规则 = 一张多平台工作单。**

电商处理的是商品、图片、视频、标题、属性、价格和译文；自媒体处理的是稿件、封面、图片、视频、标题、话题和声明。两者共用会话复用、素材库、任务编排、平台技能、发布确认、异常接管和逐平台回执。

### 1.4 简单性原则

后台能力可以复杂，用户交互必须简单：

> **用户只负责提供素材、说清目标、处理确认和异常；Sparo 负责流程、平台差异和执行细节。**

不要求用户画流程图、写脚本、理解字段映射、配置工具参数或盯着多个网页。

## 2. 调研方法与证据边界

本轮调研属于案头研究，证据来自平台规则、官方产品文档、法规和行业资料。官方产品文档能够证明“某项能力存在”和“某类规则存在”，不能证明用户痛点的发生频率、损失金额或付费意愿。

因此，本方案区分三类结论：

| 标记 | 含义 |
|---|---|
| **已证实** | 有官方规则、官方文档或权威资料直接支持 |
| **流程推断** | 可以从真实工作步骤和平台差异推导，但普遍程度尚待样本验证 |
| **待访谈验证** | 不能仅凭公开资料成立，必须观察真实用户工作或取得一手反馈 |

不得把本方案中的痛点排序当作用户访谈结果，也不得虚构节省时间、成功率或市场规模数据。

## 3. 目标人群与需求调研

### 3.1 电商人群：真实工作流

中小跨境电商从上品到在售，通常需要经过：

**趋势与竞品信息 → 找货核价 → SKU 与图片整理 → 素材加工和翻译 → 类目属性与价格填写 → 发布前检查 → 人工确认 → 平台审核 → 失败修改 → 商品链接与后续库存订单协同。**

店小秘现有官方文档已经覆盖 Ozon 的采集搬家、智能生成产品信息、类目属性匹配、模板、图片美化、俄文翻译、定价、订单、客服、退货、利润和库存等能力。[cite:1] 马帮等 ERP 也公开提供选品、刊登、订单、仓储、物流、财务等广泛功能。[cite:2]

**战略含义：Sparo 不能再造一个功能更少的 ERP。** 订单、采购、仓储、物流、财务和通用库存管理应由现有 ERP 承担；Sparo 的价值是把仍需要人盯着网页完成的差异处理、异常恢复、跨后台执行和结果验收连起来。

### 3.2 电商核心痛点与产品响应

| 核心任务/JTBD | 痛点判断 | 证据状态 | Sparo 的产品响应 |
|---|---|---|---|
| 一个商品要在不同平台发布 | 类目、属性、图片、语言和价格规则不同，同一素材不能直接机械复制 | **已证实规则差异；频率待验证**[cite:4][cite:15] | 一份商品素材生成逐平台版本，集中展示差异 |
| 上架前避免缺项和低级错误 | 必填属性、图规、资质、翻译和价格缺项会导致返工或审核失败 | **已证实规则存在；返工率待验证** | 发布前预检，缺项一次列清，不让用户逐平台试错 |
| 不想在多个后台重复检查 | 用户需要知道哪个版本改了什么，而不是重新阅读整份商品 | **流程推断** | 只呈现平台差异、风险和必须人工决定的内容 |
| 提交后还要处理审核和失败 | 上传或提交不等于平台已接受，错误定位与恢复仍是独立工作 | **Ozon 等审核机制已证实**[cite:4] | 每个平台独立回执，失败从断点续跑，禁止重复发布 |
| 想判断什么品值得上 | 趋势、货源、合规和毛利信息分散，单纯“热榜”不足以支持决策 | **流程推断；痛点强度待验证** | 后期生成选品证据卡，不承诺预测销量 |

### 3.3 电商现有工具边界

| 能力 | 现有 ERP/平台已提供 | Sparo 的战略选择 |
|---|---|---|
| 通用采集、搬家、翻译、图片美化 | 店小秘等已经提供[cite:1] | 复用，不重造 |
| 订单、采购、仓储、物流、财务 | ERP 核心能力[cite:1][cite:2] | 不进入 |
| 平台官方 API | 速卖通、Ozon 等提供授权接口[cite:3][cite:4] | 有合法接口时优先使用 |
| 跨网页理解和异常续跑 | 网页流程变化、登录墙、验证码和页面异常仍需要处理 | 核心投入 |
| 发布前差异审核和逐平台回执 | 可作为 Sparo 的统一工作单层 | 核心投入 |

### 3.4 电商合规硬约束

1688 于 2026-10-07 生效的法律声明明确要求：第三方智能体或自动化程序访问、调用或操作相关产品和服务，须事先获得明确书面许可并完成必要的安全、合规评估；同时禁止绕过验证码和人机识别。[cite:5]

因此：

- **未经许可，不把直接自动操作 1688 网页作为默认采集路径。**
- 货源进入优先使用官方授权铺货、合法 API、用户有权使用的文件或店小秘已有授权链路。
- 店小秘“采集完成后、上品前编辑”仍是现阶段的重要切入点。
- 不因用户要求而绕过平台限制；合规路径不存在时，明确停止并说明原因。

Google Trends 官方说明其数据来自随机样本，并经过归一化，反映相对搜索热度而非绝对需求或销量；官方 Trends API 当前也不能被默认视为普遍可用。[cite:6][cite:7] 因此，选品功能只能输出带来源的趋势证据，不能把“热度上涨”直接等同于“这个品会卖得好”。

### 3.5 自媒体人群：真实工作流

多平台内容工作通常包括：

**选题与事实/版权核验 → 主稿和图视频 → 标题、正文、封面、话题和声明的平台化 → 预览审核 → 登录和提交 → 平台审核 → 补漏重发 → 数据复盘。**

头条公开封面规范对比例、尺寸和图片内容有具体要求，说明平台化适配不是可有可无的包装。[cite:8] AI 生成合成内容需要按法规进行声明和标识，不能通过自动化恶意删除或隐匿标识。[cite:9]

### 3.6 自媒体核心痛点与产品响应

| 核心任务/JTBD | 痛点判断 | 证据状态 | Sparo 的产品响应 |
|---|---|---|---|
| 一份主稿适配多个平台 | 标题、封面、正文、话题和声明存在平台差异 | **已证实部分规则；整体频率待验证** | 生成逐平台变体和预览，不做机械同发 |
| 发布前保持创作者控制权 | AI 改写、原创/AI/商业声明可能改变表达和合规责任 | **规则已证实；人审偏好待验证** | 关键声明和发送由人确认 |
| 知道每个平台到底发没发成 | 登录过期、验证码、上传失败和异步审核会产生不同结果 | **流程推断** | 逐平台状态、作品 URL、失败原因和接管入口 |
| 失败后安全恢复 | 盲目重试可能重复发布或再次触发风控 | **流程推断** | 幂等重试、先查已有结果、从断点继续 |
| 发布后做复盘 | 各平台指标口径和权限不同，不能简单相加 | **IAB 资料支持，国内样本待验证**[cite:14] | 保留原生指标口径和快照，不伪造全网去重触达 |

蚁小二公开自报已支持 40+ 平台分发、多账号和统计，新榜矩阵通也公开提供任务、素材、内容和数据能力。[cite:10][cite:11] 这些资料只证明厂商宣称的功能范围，不证明实际效果，但足以说明：

**平台数量、定时队列、通用 AI 写稿和基础数据看板已经是商品化基线，不应成为 Sparo 的主要差异化。**

### 3.7 自媒体合规硬约束

《互联网信息内容多渠道分发服务管理规定》自 2026-09-01 起施行，涉及服务机构登记、平台入驻、内容管理、服务协议和行为规范，并明确禁止流量造假和批量发布同质化内容等行为。[cite:12]

因此：

- 自媒体能力不能以“批量同发”“账号矩阵无人值守”为卖点。
- 产品默认生成有实际差异的逐平台版本，并保留人工审核。
- 在正式开放多渠道分发能力前，需要由法务确认 Sparo、用户和服务场景是否落入相关服务机构义务范围。
- 不伪造阅读量、互动量或跨平台去重触达，不自动刷量。
- 小红书等平台的公开 AI 治理口径强调创作者主导，不能把 AI 托管和批量运营作为产品方向。[cite:13]

### 3.8 本轮尚不能证明的关键假设

以下问题必须通过一手调研回答：

1. 目标用户每周实际处理多少“SKU × 平台”和“稿件 × 平台”。
2. 店小秘现有翻译、属性匹配、图片和定价能力在哪些步骤仍需要返工。
3. 用户最痛的是重复录入、规则检查、发布失败，还是选品和利润判断。
4. 用户是否愿意把本机登录态交给 Sparo 执行，以及哪些动作必须每次确认。
5. 多平台创作者是否已有分发工具，为什么仍需要切换工具。
6. 用户愿意为“完成工作单”付多少钱，还是只愿为模型调用或会员付费。
7. 哪类任务能保持足够稳定的授权和平台访问条件。

## 4. 产品概念与最终形态

### 4.1 最终形态

最终产品不是布满按钮的后台，而是：

> **一个聊天框 + 一张任务卡 + 一组需要人处理的事项。**

用户把商品链接、货源文件、图片、视频、稿件或一句目标交给 Sparo。Sparo 自动识别任务类型、调用平台技能、组织后台网页执行，并返回每个平台的结果。

最终形成两条闭环：

**电商：选品证据 → 授权货源 → 商品素材 → 店小秘整理 → 多平台上架 → 商品回执 → 经营数据复盘。**

**自媒体：选题/主稿 → 平台变体 → 人工审核 → 多平台发布 → 作品回执 → 原生数据复盘。**

### 4.2 用户只需理解四个对象

| 对象 | 用户理解 | 系统负责 |
|---|---|---|
| **素材** | 商品、稿件、图片、视频和文件 | 保存来源、去重、引用和版本 |
| **任务** | 要把什么东西发到哪些平台 | 拆解步骤、选择技能和组织窗口 |
| **待我处理** | 需要确认、登录、补资料或看异常 | 只呈现必须人工决定的事项 |
| **结果** | 哪些成功、哪些待审、哪些失败 | 保存链接、回执、原因和续跑入口 |

### 4.3 一次标准交互

1. **给素材、说目标**：例如“把这个商品上到速卖通和 Ozon”。
2. **看一张计划卡**：只显示平台、交付物、缺失资料和需要确认的动作。
3. **让它执行**：后台运行，不抢占当前工作，用户可继续做别的事。
4. **处理必要事项**：登录、验证码、关键声明、发布或支付确认集中出现。
5. **收到结果**：成功给链接，待审给状态，失败给人话原因和下一步。

默认不展示工具调用、DOM、JSON、技能参数和长日志。详细过程作为可展开记录存在，不占主界面。

### 4.4 多平台与多窗口

一个聊天框管理多个后台标签和任务，但用户看到的不是窗口数量，而是一张任务结果卡：

| 素材 | 平台 | 状态 | 下一步 |
|---|---|---|---|
| 商品 A | Ozon | 已提交，待平台审核 | 查看回执 |
| 商品 A | 速卖通 | 缺少品牌资质 | 补资料 |
| 稿件 B | 百家号 | 草稿已完成 | 确认发布 |
| 稿件 B | 头条 | 登录失效 | 重新登录 |

并行只是执行手段。每个“素材 × 平台”必须有独立状态，禁止一个平台成功就把整张任务标为完成。

### 4.5 页面变化适应

Sparo 与普通固定脚本的核心区别是理解页面语义，而不是死记坐标：

- 能识别“传图入口”“标题字段”“提交按钮”等用途；
- 原入口消失时，区分未加载、权限不足、入口改名和流程升级；
- 能安全找到等价入口时继续，并记录本机经验；
- 不能确定时暂停，说明页面、步骤和需要人工判断的内容；
- 每个平台技能保留版本、最后验证时间、失败情况和已知缺口；
- 重试前检查是否已提交，避免重复商品或重复作品。

产品承诺应是“能识别并安全处理变化”，不是“任何平台升级都能自动解决”。

## 5. 阶段性功能规划

路线采用四次能力跃迁：

> **A 替代一次手工 → B 消灭重复录入 → C 支撑批量执行 → D 形成经营闭环。**

每一版必须先通过上一版的真实工作单验收，不能只做界面演示。

### 5.1 A 版：单平台可靠工作单

**阶段目标：让用户把一项完整任务交给 Sparo，而不是只让 Sparo 帮忙填几个字段。**

**新增用户价值：从“我自己操作整个后台”升级为“我只确认和看结果”。**

电商参考链路：

**合法素材输入 → 店小秘商品整理 → 发布前检查 → 人工确认 → 一个平台上架 → 回执。**

建议第一条参考平台链选择店小秘至 Ozon 或速卖通之一，以真实账号条件和黄金场景 QA 决定，不同时铺开。

核心功能：

- 商品素材包和来源记录；
- 单平台工作单与计划卡；
- 本机登录态、后台不抢焦、暂停和续跑；
- 必填资料检查与缺项清单；
- 发布前确认门；
- 成功、待审、失败三类真实状态；
- 商品链接/平台回执和失败原因；
- 自媒体仅做单平台回执验证，不分散电商主线资源。

**进入 B 版的门槛：**

- 电商黄金场景连续 10 次真实执行，完整成功率目标不低于 90%，假完成必须为 0；
- 登录、验证码、发布确认和失败接管都能正确停等；
- 结果可由商品链接、平台回执或读回内容独立核验；
- 真实用户能不看网页过程，仅凭任务卡理解结果。

以上数字是产品验收目标，不是当前能力声明。

### 5.2 B 版：一份素材，多平台复用

**阶段目标：同一份商品或稿件只输入一次。**

**新增用户价值：从“一个平台省一次力”升级为“多平台不重复录入”。**

核心功能：

- 一份商品生成两个平台的字段、图片、译文和价格差异；
- 一份主稿生成两个平台的标题、封面、正文、话题和声明变体；
- 平台规则预检和集中差异预览；
- 多平台串行执行，逐平台独立确认；
- 每个平台独立回执，失败不影响其他平台继续；
- 参考链路从单平台扩展到“同品双平台”和“一稿双平台”。

**进入 C 版的门槛：**

- 用户无需再次输入公共素材；
- 平台差异可预览、可修改、可追溯；
- 任一平台失败不会被误报为整单成功；
- 重试不产生重复商品或重复作品；
- 自媒体多渠道分发的法规适用和平台边界完成专项核验。

### 5.3 C 版：批量、多窗口与变化适应

**阶段目标：从单任务工具升级为多平台执行中控台。**

**新增用户价值：从“一次交一个活”升级为“一次交一批活，只处理异常”。**

核心功能：

- 多商品、多稿件、多平台任务矩阵；
- 后台任务池、队列、限流和独立标签执行；
- 一个聊天框统一查看全部任务；
- 集中异常收件箱：登录、验证码、缺资料、页面变化和确认；
- 断点续跑、幂等重试和单平台取消；
- 页面语义重定位、平台改版识别和安全降级；
- 技能健康度、最后验证时间、回退率和已知缺口；
- 平台技能版本化，异常时优先使用稳定路径。

**进入 D 版的门槛：**

- 批量执行时仍能逐平台验收，无批量假完成；
- 平台页面变化测试中，不死点固定位置、不盲目提交；
- 多任务之间素材、账号和结果不串线；
- 用户只需处理异常，不需要逐个窗口盯执行；
- 并发增加后，完整成功率和人工接管率不出现不可接受的恶化。

### 5.4 D 版：经营与内容闭环

**阶段目标：从执行工具升级为“人做决策、Sparo 做执行”的运营伙伴。**

**新增用户价值：从“帮我发布”升级为“告诉我为什么做、替我执行、再把结果带回来”。**

核心功能：

- 趋势、货源、竞争、合规和毛利的选品证据卡；
- 从选品证据一键转为商品工作单；
- 图片、视频和文案的进一步生成与平台适配；
- 发布后商品状态、内容数据和审核结果回收；
- 保留各平台原生指标口径，形成可追溯复盘；
- 根据真实结果生成下一轮人工决策建议；
- 在授权和合规允许时扩展更多平台技能。

**最终验收：**

- 用户能够完成“决定做什么 → 交给 Sparo → 处理关键确认 → 收到结果 → 复盘”的完整闭环；
- 北极星指标形成持续增长：每周被用户验收的有效工作单数；
- 用户持续交活并愿意付费，而不是只在首次演示时使用。

## 6. 路线总表

| 版本 | 能力跃迁 | 用户新目标 | 核心交付 | 暂不做 |
|---|---|---|---|---|
| **A** | 单点可靠 | 一个任务真正做完 | 单平台工作单、确认、回执、接管 | 多平台铺开、选品闭环 |
| **B** | 素材复用 | 一份素材发多个平台 | 平台变体、差异预览、双平台执行 | 大规模批量、复杂看板 |
| **C** | 规模执行 | 一批任务只处理异常 | 多窗口、任务矩阵、续跑、页面适应 | 自动经营决策 |
| **D** | 业务闭环 | 从决策到执行再到复盘 | 选品证据、内容生产、数据回收 | 无人值守店铺、违规矩阵 |

功能优先级必须服从这条路线。任何新功能先回答：

1. 是否缩短素材到多平台结果的路径？
2. 是否提高完整工作单成功率、减少假完成？
3. 是否减少真实重复劳动或人工接管？
4. 是否属于当前版本必须解锁的新能力？

不能回答时，不进入当前版本。

## 7. 产品边界

### 7.1 明确不做

- 不重做订单、采购、仓储、物流、财务等 ERP 核心系统；
- 不做面向所有人的通用浏览器竞争；
- 不做未经许可的数据采集和平台操作；
- 不绕过验证码、人机识别、平台风控或访问限制；
- 不做指纹多开、虚假账号矩阵、刷量或批量同质化内容；
- 不承诺无人值守下单、支付、店铺经营或内容互动；
- 不把趋势热度包装成销量预测；
- 不为了自动化率取消关键人工确认。

### 7.2 人工与自动的分工

| 人负责 | Sparo 负责 |
|---|---|
| 决定上什么品、发什么内容 | 搜集证据、整理素材和执行流程 |
| 确认价格、资质、版权和关键声明 | 检查缺项、生成平台版本和提示风险 |
| 登录、验证码和必要授权 | 复用合法会话、后台执行和不抢焦 |
| 发布、支付、删除等关键决策 | 默认等待确认并保存回执 |
| 处理无法安全判断的异常 | 定位异常、保留现场、支持续跑 |

自动执行模式可以减少发布打断，但支付、删除、登录和验证码等边界不因版本升级而自动消失。

## 8. 指标体系

### 8.1 北极星指标

**每周被用户验收的有效工作单数。**

“有效”必须同时满足：交付物齐全、结果可核验、没有假完成、用户认可该任务有实际价值。

### 8.2 核心指标

| 指标 | 定义 |
|---|---|
| 完整工作单成功率 | 所有必需平台步骤和交付物均完成的比例 |
| 假完成率 | 声称完成但缺回执、缺链接或缺计划步骤的比例，目标始终为 0 |
| 人工接管次数 | 按登录、验证码、缺资料、确认和页面异常分类 |
| 单位有效工作单成本 | 每个有效结果消耗的模型、时间和工具调用 |
| 素材复用率 | 同一素材被多个平台有效复用的比例 |
| 技能回退率 | 平台技能失效后改为临场操作或人工处理的比例 |
| 重复发布事故 | 因重试或状态误判造成重复商品/作品，目标为 0 |
| 持续交活率 | 用户在后续周期继续提交真实工作单的比例 |
| 付费验证 | 用户是否愿意为真实完成的工作单持续付费 |

不以平台数量、窗口数量、工具调用数、Token 数或界面功能数作为成功标准。

## 9. 一手需求验证方案

案头调研之后，先验证再扩大功能范围。

### 9.1 样本

- 电商：12 名近 30 天有真实上品工作的运营者，覆盖店小秘用户、速卖通/Ozon 等平台和不同 SKU 量级。
- 自媒体：8 名近 30 天持续向至少两个平台发布图文的创作者或小团队成员。
- 样本必须来自真实工作场景，不能只访问对产品概念感兴趣的人。

### 9.2 调研方法

1. 让用户演示最近一次完整任务，不只问“想要什么功能”。
2. 记录每一步耗时、切换工具、复制内容、返工和失败原因。
3. 收集脱敏后的商品字段、图片规范、发布回执和错误样例。
4. 记录现有 ERP、分发工具和人工外包的使用成本。
5. 用 A 版工作单完成真实任务，再观察用户是否愿意继续交活和付费。

### 9.3 必须产出的证据

- 电商与自媒体各一张真实工作流图；
- 每个核心痛点的实际样例、频率和后果；
- 现有工具已经满意解决的部分，避免重复开发；
- A 版参考链路的真实账号与平台条件；
- 必须人工确认的节点清单；
- 用户是否愿意为“结果”而非“模型”付费的证据。

### 9.4 战略复核条件

出现以下情况时，应收窄或调整路线，而不是继续堆功能：

- 目标用户现有 ERP 已充分解决问题，Sparo 没有稳定增量价值；
- 核心链路长期缺少合法稳定的授权或执行路径；
- 人工接管过多，用户仍需全程盯守；
- 用户愿意试用但不愿持续交活或付费；
- 自媒体合规义务使产品形态不再适合小规模团队。

---

## 10. 当前落地决策

1. **产品主线改为电商自动化执行，自媒体复用同一底座。**
2. **第一版只验证单平台完整工作单，不同时铺开所有平台。**
3. **店小秘是中枢，不是被替代对象；Sparo 做跨后台理解、执行、异常和验收。**
4. **1688 等货源侧优先官方授权链路，未经许可不直接自动操作。**
5. **交互只保留素材、任务、待我处理、结果四个用户概念。**
6. **A 版真实黄金场景通过前，不把多平台并行作为宣传重点。**
7. **现行产品文档中的通用浏览器定位、电商边界和原版分工需要另行统一，避免对外口径冲突。**

最终判断标准：

> **Sparo 不以“能操作多少网页”为成功，而以“多平台运营者每周愿意把多少真实工作单交给它”为成功。**
