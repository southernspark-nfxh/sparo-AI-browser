## 2. 已定方向

1. 一个 Mission 在任一时刻只有一个运行时写它。`executeMission()` 与 `runLlmGoal()` 不得交错写同一张单。
2. 模型决定下一步。本地只校验工具是否存在、参数、权限、预算和硬结构。
3. 工具执行成功不等于目标完成。复杂任务由独立 Verifier 做语义验收，Close Guard 再查硬交付。两者都过才 `close.reason=done`。
4. 工作单保留：思路卡、计划、证据、挂起、恢复。不另做一套聊天产品。
5. 第一个业务切片是多信息调研（采集、证据、报告、验收）。旅行、表单、发布排在后面。
6. 完整路径是默认。轻量路径只给单交付、单动作、无长采集、无多来源、无报告或文档、无外部写操作的任务。
7. 发布、发送、付款和其他外部写操作始终走完整验收。当句授权只说明人允许做这个动作。
8. G6 只要产出报告或文档，走完整路径。
9. `research_mission`、`trip_plan` 是模型写进计划的必跑专用步。Close Guard 核对它们真实执行。Runtime 不在问模型之前替它抢跑。
10. 旧的「报告单先跑 mission 整手、旅行单先跑 trip_plan 整手」留在 legacy。调研整手在 M2-01 开工前、旅行整手在 M3-03 开工前，分别写入 `docs/DECISION-POINTS.md` 并评审。旧强制分支仍须等验收后才删：调研整手等 M2-04 的 G4/G8 通过，旅行整手等 M3-03 逐段对账通过。
11. M1 只证明内核：无依据推断不能 done。报告上可见的「推断」标记和依据展开属于 M2-03。
12. 预算耗尽、Verifier 连续不通过、可恢复异常进入 `blocked`，不写 `close`。原因分别是 `budget_exhausted`、`verification_exhausted`、`error`。
13. `close.reason=cancelled` 只表示用户主动取消或放弃。`close.reason=incomplete` 只表示用户看过缺口后明确要求按现状结束。`close.reason=runtime_rollback` 只表示运行时紧急回滚。系统不得把预算停止或验收失败写成这三种终态。
14. `blocked` 到期只提醒，不自动关单。保留期长短是 O-06，M3-02 之前定稿。
15. 只有 `STORE_CHANNEL=msft` 隐藏价格、套餐和付款界面。其他渠道保持现行本窗口套餐。任何渠道都不把云端 Key 打进客户端。本次不改定价和支付。

## 3. 相对第三轮产品书的三处收紧

这三处是执行合同。M0-03 把它们写回产品书对应段落。

**成本。** 组合成功成本的分子包括：成功单、失败单（含 `close.reason=incomplete`）、用户取消单、运行时回滚单，以及仍为 `blocked` 且原因为 `budget_exhausted` 或 `verification_exhausted` 的单。同一 Mission 在冻结截止时只计一次。分母是成功单数。成功数为 0 时只报告总成本和样本量，不做除法。真实完成率的分母分开列出已关单与未关单 `blocked`，不停在预算或验收上的单不得从指标里消失。只有 500 字截断 finding、没有可按区间重读的全文 Artifact 时，O-01 的 Token 数保持 `[TBD]`，M1 不得进门。

**入句。** 现行 `runtime.ts` 把一切 `state=blocked` 当成补槽追问。v2 必须先看 `blocked.reason`。只有 `missing_input` 走补槽。`budget_exhausted`、`verification_exhausted`、`error`、`needs_decision` 走恢复选项，不把「继续」或一个城市名填进槽位。O-04 的界面映射同样按这个原因分支。

**M2-01 完成定义。** v2 路径不在询问模型之前做整手抢答。legacy 里 `executeMission()` 的 mission / trip_plan 强制分支继续保留，直到第 2 节第 10 条的退役条件成立。M2-01 完成不等于删除这段旧代码。

## 4. 明确不做

- 不把 v2 Loop 写进 `browser.ts`，直到第 5 节的 M1 门通过。
- 不一次性重写 `browser.ts`。
- 不让 legacy 与 v2 同时写同一 Mission。Mission 创建时固定 `runtime`，中途不热切换。
- 不新增 MissionState。不把 `incomplete` 做成状态。
- 不用正则或句式表判定任务类型，也不为了修轻量误判去加这种表。
- 不用文本长度、`covers` 或计划自声明作为完成证明。
- 不跳过新任务思路卡。不自动处理登录、验证码、付款。不默认自动发送。
- 不引入新的模型供应商，不改 `sparo-pay`，不把云端 Key 放入客户端。
- 不建设云沙箱、长期个人记忆、通用子 Agent 平台或 MCP 市场。
- 不用单元测试代替黄金场景，不在安装包复测之前发布。
- 不编造基线数字。没有样本就保持 `[TBD]`。

M1 门三条，缺一条就停：

- 拆分门：调用图、共享状态写入口、副作用清单、分刀顺序、每刀的回滚点。Mission 写者有两处说不清，门就不通过。
- 成本门：M0-05A 的回放输入能按区间重复读取，M0-05B 给出分任务类型、分结果的成本。输入或结果类不够则 O-01 继续 `[TBD]`。结果类不要求在只读采样里出现。
- 发布门：O-07 写明 A、B、C 或「暂不提审」，并写明提审 runtime 和允许进包的切片。

## 7. Trae 用这些条件打回

看到下面任一条，方向已经偏了，停下来打回，不要接着补代码：

1. M1 门通过之前，出现写入 `browser.ts` 的 v2 Loop。
2. 用 500 字 finding 填出 O-01 的 Token 数，或把离线 Verifier 的对照成本算进真实 Mission 成本。
3. 预算耗尽、验收失败或普通错误被写成 `cancelled`、`incomplete` 或侧栏上的「用户取消」。
4. 一切 `blocked` 仍走补槽，预算阻塞时一个城市名或「继续」被填进槽位。
5. M1 的退出条件要求报告界面上的推断标记。
6. M2-04 之前删除 `executeMission()` 的调研整手强制，或 M3-03 之前删除旅行整手强制。
7. 发布、发送、付款或外部写操作走了轻量路径。
8. 同一 Mission 上 legacy 和 v2 都在写。
9. 非微软渠道的套餐或付款界面被拆掉，或客户端包进云端 Key。
10. 新增本地句式表、站点特例，或用长度 / `covers` 判完成。
11. 没有你的选择，却把提审方案落成 A、B 或 C。
12. 在原版仓库 `D:\download\Sparo` 改这套任务循环。
13. 组合成功成本的分子漏掉 `incomplete`，或同一 Mission 在冻结截止时被计了两次。
14. M2-01 或 M3-03 开工前，对应整手还没有写入 `docs/DECISION-POINTS.md` 并评审。
