## 一、补审结论

**补审执行完成；0.7.7 开发版验收结论：阻断，不可签收。**

阻断依据不是“整个 Agent 已失效”，而是以下问题仍然成立：

1. 店小秘专用链路的关闭文案和蒸馏技能工具合同仍有 P0 缺陷；
2. S-01 的自动发布授权与任务书安全基准冲突，且 FreeSoul 下 `click_text` 的本地发送门会直接放行，不能独立证明 step 模式一定经过确认往返；
3. 新增 S-02：`dxm-crawl-prep` 的普通“保存”未声明为人工门，非蒸馏技能可通过 `execute` 直接点击保存，静态调用链中未见独立保存确认；
4. R1、R2、R3 分别被店小秘登录/滑块验证和头条未登录阻断，正常编辑、填稿及草稿保存闭环均未验证。

R4 已在 0.7.7 开发版真实证明：内置 FreeSoul 缺少新建标签能力会导致“同时保留两个目标页面”的用户目标失败，因此原 P2-01 升为 P1。

**最终开放项统计：P0 × 2，P1 × 5，P2 × 0；另有独立安全项 S-01、S-02。** 其中多项为“静态确定、真机未验证”，不冒充动态复现。

本报告只支持 0.7.7 开发版增量判断；**安装包验收另行执行**。

### 3.2 M2：失败分支与本地改判

最小调用链：

```text
FreeSoul 模型选择 run_skill
  → free-soul.ts safeRun()
  → browser.ts runSkillTool()
  → runner.ts runSkill()
      ├─ 蒸馏技能：返回路线 + data.agentPlaybook，不执行其中 execute
      ├─ 非蒸馏技能：逐步 runOneStepWithRetry()
      ├─ 步骤失败：返回 { ok:false, message, data.log/diagnose }
      └─ pause：返回 { ok:true, data.paused:true }
  → ToolResult 回到 FreeSoul 消息循环
  → 模型可改用通用工具；safeRun 异常也转成 ok:false，而非直接终止整个 Agent
```

关键源码：

- `src/main/skills/runner.ts:1257-1302`：找不到技能、预览关闭、无步骤分别返回 `ok:false`；蒸馏分支只返回剧本。
- `src/main/skills/runner.ts:1346-1384`：步骤失败终止当前技能并返回日志和诊断。
- `src/main/skills/runner.ts:1386-1391`：`pause` 是 `ok:true` 且带 `paused:true`，不能与 `ok:false` 混为一类。
- `src/main/skills/runner.ts:1017-1020`：`execute` 由 runner 直接调用浏览器能力。
- `src/main/agent/free-soul.ts:245-246`：明确“失败时不要停，改用通用工具继续”。
- `src/main/agent/free-soul.ts:826-835`：`safeRun` 把异常转成工具结果回传模型。
- `src/main/agent/free-soul.ts:253-260`：`run_workflow` 描述仍把 `ok:false` 或 `waiting_human` 泛化为停等。
- `src/main/agent/free-soul.ts:312-316,646-648,818-823`：重复操作/页面停滞提示、软轮次和 100 轮安全上限存在。

本地与模型的边界：

- `src/main/agent/kernel/reasoner.ts:567-586`：本地已经产生 `ask/propose/synthesize` 或无下一步时直接返回，不再询问模型。
- `src/main/agent/loop.ts:249-273`：缺槽产生 `ask`；`goal.needsConfirm` 转为 `propose`，不是 `slotAsk`。
- `src/main/agent/loop.ts:468-523`：模型理解失败回退本地 heuristic；`coverage:"new"` 的新计划会设置 `needsConfirm:true`。
- `src/main/agent/loop.ts:604-686`：本地 `planForGoal/compileHands` 和合法 cap 校验存在，不能笼统称“本地没有计划或改判能力”。
- `src/main/agent/runtime.ts:638-726`：确认、继续、补槽使用已存目标推进本地状态机；新任务/修订在 `applyTurnAsyncBody` 中调用 `analyzeGoal`。
- `src/main/agent/runtime.ts:794-805`：异步结果仍受 `stillWanted` 和日志落盘约束，晚到结果不会无条件覆盖新状态。

`intent-router.ts` 未命中处理：`routeUserGoal()` 在 `src/main/agent/intent-router.ts:492` 返回 `null`，交还后续模型/FreeSoul，不是必然终止。中文能力提示在第 511 行已允许直接贴标题正文或先打开编辑器；英文第 526 行仍要求平台与目录，规则未完全同步。

结论：P1-03 保留但仅指 `run_workflow` 的过宽停等语义；不得写成“所有工具失败都会中断 Agent”。P1-02 的影响面仍是旧工作单、英文提示和技能消费者，R2/R3 的 FreeSoul 行为不能被这些静态残留抹掉。

### 3.3 M3：追问分类与普通字段边界

| 机制 | 产生条件 | 补审判断 |
|---|---|---|
| `ask` | `sealWorkOrder` 发现合法槽位缺失；旧发稿路径包括 `articleDir` | 缺平台是合理问题；已有内联标题正文仍强制目录则不合理 |
| `slotAsk` | 对首个 `blockedSlot` 生成具体问句 | 是问句格式化机制，不应单独视为模型决策 |
| `needsConfirm → propose` | 本地行程确认或模型给出新计划 `coverage:"new"` | 属于方案确认，不等于缺槽，也不等于安全门 |
| `request_confirm` | FreeSoul step 模式的发布、发送、支付、删除等不可逆动作 | 应保留；S-01 表明本地发送门并未独立强制该往返 |
| 登录/验证码/`waiting_human` | 页面需要人或技能明确人工门 | 合理停等，不能为追求自主性绕过 |

普通字段不能一刀切：

- 标题草案、已有属性的语言转换、可逆的页面选项，可先依据页面和历史给草案，再汇报假设；
- 重量、尺寸、库存等若来源页面有可靠事实可提取并换算，读不到或来源冲突时不能编造；
- 品牌授权、HS/申报信息、欧盟或土耳其责任人、资质等法律或用户事实，无法可靠推断时应问；
- 保存、认领、发布、付费、删除是独立硬边界，不因字段可自决而自动获得写入授权。

P1-01 的 0.7.6 历史真机观察仍有效；R1 没有进入编辑态，所以 0.7.7 正常视口下是否仍追问保持未验证。

## 七、S-01 独立安全结论

### 7.1 结论

**S-01：阻断。** auto 模式的授权规则与“真实发布必须人确认”的任务书基准直接冲突；同时，本地 `click_text` 发送门在 FreeSoul 运行时直接放行，使 step 模式的独立确认也不能仅由该门禁保证。

### 7.2 step 与 auto 的实际授权链

| 模式 | 模型规则 | 实际本地门 | 补审判断 |
|---|---|---|---|
| step | `free-soul.ts:376` 要求发布、发送、支付、删除前 `request_confirm`；`716-723` 截获确认并结束本轮等待用户 | `publish-gate.ts:28-34` 对 `freeSoulRunning && send` 直接返回 `ok:true`；`browser.ts:12227-12228` 实际传入 `this.freeSoulRunning` | 模型正常遵守提示时会确认，但本地门不能独立阻止“未确认就 `click_text('发布')`”的调用；确认主要依赖模型遵守，而非完整硬门 |
| auto | `free-soul.ts:403-412` 明确“发布、发送类动作直接执行，不调用 request_confirm——用户下达的任务指令本身就是授权” | 同一 FreeSoul send 分支直接放行 | 与任务书安全基准明确冲突，阻断 |
