## 1. 不可漂移的边界

1. 不提交 Git，不运行 `npm run dist`，不覆盖或回退工作区其他任务的改动。
2. 不对真实账号执行字段赋值、分类、认领、图片处理、翻译、保存或发布；只跑纯夹具和 mock port。
3. 不把 `dxmEnabled()` 改成 true，不把四个新 ID 加进旧 `WORKFLOWS`，不调用旧 `runFullListing()`。
4. 不接回旧 `executeMission`、旧意图路由、旧工作单循环或 `parseLocalIntent`。
5. 不用本地正则、关键词或固定规则替代模型理解用户意图。新增会提前结束或改变任务走向的本地判断，先登记 `DECISION-POINTS.md`。
6. 保存、提交、待审、结果未知都不是上线；只有同一平台商品 ID 的在线读回或可核验在线链接才能进入 `published_online`。
7. 当前 live 写适配器停等不代表可以放宽 mock 中的安全合同。mock 必须按未来真实适配器的约束实现。
8. 不顺手实现真实选择器、批量、多平台或第二阶段能力。

## 2. 修复任务

### R1-1：收费动作必须有本次、可信且范围一致的确认

**当前问题：** `dxm-smt-images.ts` 对任意非空且不含拒绝词的文本都可能执行，例如“等待确认”。

**修改要求：**

1. 删除“非空且没有拒绝词就执行”的逻辑，不得用本地关键词情感判断代替 #28。
2. 收费执行必须能证明本次顺序为：模型 `request_confirm` → 用户下一条明确同意 → 工作单、收费功能、图片范围和可读费用信息未变化。
3. `paidConsent.text` 或模型自报的“用户已同意”不能单独作为可信凭据。优先复用 Free Soul 本次确认往返的上下文；如需一次性确认句柄，必须绑定本次 `request_confirm`、工作单、功能和范围，不得保存通用“已确认”布尔值。
4. 缺失、模糊、伪造、过期、跨工作单、跨功能或范围变化的确认均不得调用 `port.translateImages`。
5. 一次收费确认不得授权另一次收费动作，也不得替代最终发布确认。逐步确认和 auto 都遵守此规则。
6. 停等时保留可靠 checkpoint，并用工作单 ID 说明下一步。

**必补测试：**

- 未确认、空文本、“等待确认”、任意非空文本、模型自报同意均不执行；
- 工作单、功能或图片范围变化后不执行；
- 合法本次确认只执行对应动作一次；重复使用不执行；
- 收费确认不能调用发布。

### R1-2：发布强制绑定标签、来源、草稿和店铺身份

**当前问题：** 发布读回和点击使用 `port.tabId`，但只检查旧 `editTabId`；同内容的另一张草稿可能被误操作。

**修改要求：**

1. 发布前确认当前执行标签就是工作单 `editTabId`；不一致立即停等，不得在新标签继续写或点击。
2. 每次发布读回必须精确匹配来源记录 ID、认领草稿 ID、目标店铺 ID 和预期编辑 URL。关键身份缺失或为空不能当作“已匹配”。
3. `editTabWritable` 不能只证明“另一张绑定标签仍可写”，必须约束实际执行标签。
4. 认领前后核对来源关系；`claim` 返回的店铺与用户目标不一致时不得进入编辑。
5. 用户指定店铺名称但列表无精确匹配时不得默认唯一店；多家、零家或授权不清均停等。

**必补测试：**

- 准备后切换 Agent 标签，发布点击数为 0；
- 同店、同标题、同字段但不同草稿 ID，发布点击数为 0；
- 来源记录、店铺或 URL 任一不匹配均停等；
- 认领返回错误店铺时不得继续。

### R1-3：指纹覆盖全部关键内容，点击前重新完整 QA

**当前问题：** 指纹未覆盖动态 `fields`、描述和图片状态，发布只比对旧 QA 与旧摘要。

**修改要求：**

1. 指纹覆盖标题、动态字段、描述、主图/变种图/描述图及其处理状态、SKU 顺序与内容、店铺、运费模板和页面身份。
2. 保留稳定规范化：固定键排序、空白、数字格式及明确的图片/SKU 顺序规则；相同业务内容指纹一致，任一关键内容变化指纹变化。
3. `dxm_smt_publish` 在写 `publish_attempt_started` 前重新读取探针和字段，并重新执行完整 QA；不能只复用准备阶段结果。
4. 动态必填项缺失、字段未读回、图片失败、权限/合规缺项或身份不一致时，指纹即使碰巧相同也不得发布。
5. 修改后必须重新 prepare、重新 QA，并在逐步确认模式重新确认。

**必补测试：**

- 修改动态材质、描述、SKU、模板后指纹变化且不能发布；
- 图片 src 不变但状态由成功变失败，不能发布；
- 准备后出现新动态必填项，不能发布；
- 无变化重复计算指纹保持一致。

### R1-4：同工作单所有读写流程防止旧快照覆盖新状态

**当前问题：** 只有 publish 串行；prepare 可在 publish 写入待审后，把旧草稿快照覆盖回去，引发再次发布。

**修改要求：**

1. 同一工作单的 prepare、publish 和会写回状态的 status 必须串行；不同工作单不必全局串行。
2. 保存前重新加载最新工作单，使用版本号、revision 或等价 CAS 防止旧快照覆盖较新的发布尝试、回执、checkpoint 或在线证据。
3. 锁内需要查询状态时抽取内部无锁 helper，避免 `runPublish` 调用 `queryExisting` 造成死锁。
4. 旧流程返回时如果版本已变化，只能返回最新可靠状态，不得保存旧状态。
5. 保留现有发布前 `publish_attempt_started`、点击后 `publish_clicked` 和结果未知禁止重试。

**必补测试：**

- 用 deferred promise 让 prepare 在持锁点暂停，同时调用 publish；prepare 未释放锁前 publish 不得点击。恢复并完成 prepare 后，publish 才继续，最终点击总数为 1，状态不得被旧 prepare 快照覆盖；
- 单独在持久化层模拟旧 revision 写入，CAS 必须拒绝其覆盖较新的发布尝试或 receipt；
- status 写回不能覆盖更新的发布尝试或 receipt；
- 不同工作单仍可独立执行。

### R1-5：补齐崩溃恢复、拒绝后修复和上线状态迁移

**当前问题：** prepare 没有恢复 checkpoint；查询忽略提交/失败记录和平台商品 ID。测试在发布前预填 `platformProductId=P1`，掩盖了问题。

**修改要求：**

1. `waiting_human` / `failed` 有可靠 checkpoint 时，prepare 先恢复其可靠状态再续跑；不能永远停在原状态。
2. 平台拒绝后必须重新读取并编辑，重新生成 QA 和指纹；不得沿用旧发布确认。
3. 查询按可靠证据关联同一工作单：
   - 提交记录可进入 `submitted_pending_review`，并保存读回的平台商品 ID；
   - 失败/拒绝记录进入 `failed`，保留拒绝回执和 checkpoint；
   - 与同一平台商品 ID 对应的在线证据进入 `published_online`。
4. 点击后崩溃形成的“提交结果未知”也允许通过查询解析为待审、拒绝或上线；证据不足时继续禁止再次点击。
5. 不得把无来源关系的“最新在线商品”归到本工作单。
6. 修改测试夹具：正常新草稿不得预填平台商品 ID，平台 ID 应由提交或在线读回获得。

**必补测试：**

- 无预填平台 ID：点击后无 productId → 查询提交记录得到 ID → 待审 → 在线读回同 ID → 上线；
- `publish_clicked` 后崩溃，恢复查询可正确关单，期间不重复点击；
- 平台拒绝后重新 prepare，旧 QA/指纹失效；
- 其他商品的在线记录不能使本单上线；
- E11 缺资质补完后能从 checkpoint 续跑。

### R1-6：认领幂等、动作证据与来源真实性

**修改要求：**

1. 认领前在目标速卖通店铺采集箱查同源草稿；已存在则读回复用，无法判重停等，不默认再点。
2. 认领副作用前持久化工作单和 `claim_attempt_started`；认领后记录结果。若平台已成功但本地结果未落账，恢复时先查目标箱，不得重复认领。
3. 多个同源未关工作单属于身份歧义，必须停等，不得返回 null 后新建另一单。
4. 认领、分类、写字段、图片/文字翻译、保存和发布逐项记录 `observed / changed / verified`；保存草稿需要独立回执或读回。
5. `asStoredProvenance` 不得把 suggestion 改成 readback。保留原始来源，实际读回写入 `verified` 和证据。
6. 工具失败或读回不匹配时不得写“已验证”；工具 ok 与业务状态继续分离。

**必补测试：**

- 认领成功后、本地落账前模拟崩溃，恢复不重复认领；
- 多同源工作单停等；
- 每个副作用动作都有三层证据，失败动作无虚假 verified；
- suggestion/user/approved_rule 来源不会被改写成 readback。

### R1-7：接通文字翻译并验收分类结果

**修改要求：**

1. prepare 实际调用 `port.translateText`，与图片翻译分开记录、分开验收；摘要不得再固定写“未发起”。
2. 文字翻译后读回标题、动态字段和描述；空译文、超长、SKU 变量丢失或失败项进入缺项/风险，不得 QA 通过。
3. 合法品牌和专有名词仍按原任务书处理，不用简单“含中文即破坏”的规则。
4. 检查 `selectCategory` 返回结果并读回目标分类；失败或分类不一致时停止后续写操作。
5. 不因此自动执行任何收费图片功能。

**必补测试：**

- 文字翻译成功与图片翻译分别记录，任一失败不能抵另一项；
- 文字翻译返回失败或读回为空时 QA 不通过；
- 分类选择失败、分类读回不一致时不再写字段；
- 准备摘要准确反映文字翻译状态。
