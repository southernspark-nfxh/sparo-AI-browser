### 2. t11 嫌疑

`1bc62e8` 的任务条改动是过滤显示，不是给底账写 close。

`task-pool.ts` 的 `finish` / `dismiss` 把卡从内存数组里摘掉。`visible()` 只留 `running`、`queued`、`waiting_human`，做完的卡不再返回。这笔 diff 没有调用 `journalMissionClose`。`browser.ts` 在这笔里新增了一处 `journalMissionClose(current.id, "done")`，是收尾路径，不是任务条过滤。

结论：任务条变干净，不能解释 45 张未关单。未关单来自开了单却没写 close，主路径是上面的双 `applyTurn`。t11 的过滤和底账 close 是两件事，阶段 2 要并存，不能互相顶替。

### 3. 恢复卡现在怎么选

`offerMissionRecovery`（已提交的 `browser.ts` 5747 行）把 `replayMissions()` 的最后一张未关单摆出来。回放规则是：没被 close、状态也不是 done/cancelled 的都算。不看有没有 turn，不看是不是同句用户话的影子单。所以存量 45 张里最新的那张，重启就会出现。说「算了」只 close 这一张（5760 行，理由「算了」）。

### 4. 关联键

没有 parent，没有 session，没有单独的 goal id。`ActiveMission` 只有自己的 `id`，加上 `raw` 和 `goal`。`AgentGoal` 有 `raw`、`intent`、`kind`，没有把两张单拴在一起的字段。

同一句用户话派生的两张单，能对上的是 `mission.raw`（两边都写入了这句原话）。31/45 张未关单能用这个对上一条已 close 的单。按时间相邻去配对不可靠：验收时几句连发，8 秒内会把不同原话的单凑成一对。

阶段 2 若照拍板退而用关联键：代码里没有更强的键，只能用「同一句 `raw`」。没有 session 字段，做不到「同一 session 内」。这一组的 close 只覆盖当场说「算了」的那句，不回溯关旧单。
